## 1. ★ 重要勘误：网格视窗**官方就有虚拟化**，没有 2000 项上限

**主文件 §4.6 的「网格视窗列表项 = 2000（无虚拟化）」需要更正**——
那是 `miliastra-beyond-simulator` **模拟器自己的实现策略**，不是官方行为。

### 官方原文（《网格视窗控件》，`mhfkrr0i7gds`，第二节「实现原理」）

> 「网格视窗的列表采用**复用列表结构**，**出于性能考虑，仅会加载处于可见范围内的列表项**。
> - _网格视窗列表发生滚动时：_ 对列表项内容进行**刷新（触发回调）**，
>   可以使用接口 `RefreshItems` 触发，从而实现滚动到对应位置时，显示准确列表项内容的效果。」

来源：`https://act.mihoyo.com/ys/ugc/tutorial/detail/mhfkrr0i7gds`

### 为什么这条很重要

1. **官方是虚拟化的**（只加载可见范围），所以「列表项数量」在**官方实现里不是性能瓶颈**；
   `studio/docs/control-support.md:41` 的「完整实例化，未做虚拟列表；单次最多 2000 项」
   是 **MBS 模拟器的保真缺口**，**不能拿它当官方容量上限用**。
2. **但 `RefreshItems` 是必需的，不是可选的**：
   因为列表项被复用了，滚动到新位置时**必须**由 `RefreshItems` 回调重新填内容，
   否则会看到**上一个位置的内容残留在新位置上**。
   → 这解释了为什么官方把 `RefreshItems` 写成「刷新**并逐项调用回调**」。
3. **列表项必须来自「列表项来源」的模板引用**，官方另有明文：
   > 「_引用控件模板：_ 网格视窗的列表项将以此控件模板为基础显示
   > **注意：仅配置在列表项来源中的模板可应用网格视窗的列表滚动效果，
   > 配置在网格视窗层级下的控件不会应用此效果**」
   → 这正式确认了主文件 §2.9 引 MBS 的那句「静态子控件保持原位」——
   **官方原话就是「配置在网格视窗层级下的控件不会应用此效果」**。

### 对检查清单的影响（主文件 §7.E）

- **E8 应改写**：把「网格视窗列表项是否可能超过 2000？是否有可见区虚拟化？」
  改为 → **「列表项内容是否全部通过 `RefreshItems` 回调填充（而不是在模板上写死）？
  预期：是。违反：滚动后列表项复用，会显示上一个位置的内容（错位/串数据）。」**
- **E9 可从【社】升为【官】**：官方原文已确认「配置在网格视窗层级下的控件不会应用滚动效果」。
- **新增 E10**：「网格视窗的列表项模板是否**只**通过『列表项来源』引用（而不是把控件直接摆在网格视窗层级下）？
  预期：走『引用控件模板』。违反：那些控件**完全不参与滚动**，会固定在原地。」

## 2. ★ 新答案：客户端 Lua **没有**定时器 API；但 `os.clock` **可用**

主文件 §4.7 / §8.2 曾把这条列为「未能确认」。现在可以定论。

### (a) 没有定时器 API —— 官方 API 文档 §6 `game` 表**通篇无** timer/schedule 函数

已逐行核对官方《客户端控件API文档》（`mhtakr07vej4`）§6「game」的四个子表：
`(1) UI 与层级`、`(2) 输入与聚焦`、`(3) 补间动画、服务器信号与自定义变量`、
`(4) 关卡、音效与本地化` —— **没有任何** `Delay` / `Timer` / `Schedule` / `SetTimeout`
一类的函数。（第 (4) 组只有 `PauseLevelTime`、`IsLevelTimePaused`、`PlayAudio2D`、
`StopAudio`、`IsAudioAlive`、`GetLanguageType`、`GetStageMode`、`IsTestPlay`、`GetText`。）

→ **结论（【官方】）**：客户端 Lua 里要做延时，**只能**用 `OnUpdate(dt)` 自己累计时间。

### (b) `os.clock` **是可用的** —— 官方裁剪是「白名单式」表述

官方原文（`mhtakr07vej4` §三「运行环境」）：

> 「以下标准库能力不可用：
> `string.dump` / `io.*` / `coroutine.*` /
> **除 `os.time`、`os.date`、`os.clock`、`os.difftime` 外的 `os.*`** /
> 除 `debug.traceback` 外的 `debug.*`」

**「除 A、B、C、D 外的 `os.*` 不可用」= A/B/C/D 可用**。
所以 `os.time` / `os.date` / `os.clock` / `os.difftime` **四个都在**，
`math.isnan` / `math.isinf` 是**额外补充**的。

⚠️ 但注意：`os.clock` 是 **CPU 时间**，不是墙钟，也不代表帧时钟。
**【推断】**做游戏计时仍应以 `OnUpdate(dt)` 的 `dt` 累加为准
（MBS 也强调「计时**显式使用 `dt`**」，`references/05-lua-implementation.md:35`），
`os.clock` 更适合做**性能自测**（量一段代码耗时）。

## 3. ★ 新答案：**没有滚轮事件** —— 只有拖动

主文件 §4.7 / §8.2 曾把这条列为「未能确认」。现在可以定论。

### (a) 官方 API 里没有任何滚轮输入 API

- 《客户端控件API文档》§3（全局 API）、§11（枚举系统）、§13.(5)（键鼠/手柄按键事件）
  里**只有按键事件**：`AddKeyEventListener(eventType, callback)`，
  而 `Enum.KeyEventType` 的全部成员都是 **键盘按键 / 手柄按键** 的 Down/Up
  （`KeyboardCraftspersonKeyNDown/Up`、`ControllerCraftspersonKeyNDown/Up`、`MouseLeft` 系）。
  **没有 `Wheel` / `Scroll` 类的事件类型。**
- 另用 `get_node_info(["滚轮"])` 查询节点库 → **`matches: []`（零命中）**。

→ **结论（【官方】）**：**没有通用滚轮事件**。
`Enum.ScrollDirection`（`Horizontal`/`Vertical`）是**网格视窗/文本视窗自身的滚动方向配置**，
**不是**输入事件。

### (b) 光标事件里有**完整的拖动生命周期** —— 自绘滚动的正确做法

官方 `Enum.CursorEventType`（§11.(7)）成员：

| 枚举值 | 说明 |
|---|---|
| `CursorDown` | 光标按下 |
| `CursorUp` | 光标抬起 |
| `CursorEnter` | 光标进入检测区域 |
| `CursorExit` | 光标离开检测区域 |
| **`CursorDrag`** | **光标拖拽** |
| **`CursorBeginDrag`** | **开始拖拽** |
| **`CursorEndDrag`** | **结束拖拽** |
| `CursorClick` | 完成点击 |

并有 `CursorEventData`（§19）提供字段与方法（坐标/位移等）。

⚠️ **前置条件（官方明文，两处）**：
- 容器节点控件：`showCursor` ——「是否显示常驻光标；**`CursorEvent` 相关方法都需设置该参数
  为真后才可正常使用**」（`mhtakr07vej4` §24）。
- 容器节点控件文档亦写：「_显示常驻光标：_ 使光标常驻显示」
  （`mh3qqq9xc102` §2.1）。

→ **结论（【官方】）**：**自绘滚动的唯一可行路径 = 光标检测区域 + 拖动事件**
（`CursorBeginDrag` → `CursorDrag` → `CursorEndDrag`），
**且祖先容器节点的 `showCursor` 必须为 `true`**。
本项目 `lua/engine_adapter_qianxing.lua` 里做铅垂滚动热区，方向与之一致。

## 4. 新答案：`Enum.TextVerticalAlignment` 的居中值是 **`Middle`**，不是「1」

主文件 §8.2 第 11 条引 MBS「居中值 **1** 是**待实机验证的推断**」。
官方 API §11.(15) 给的是**具名枚举**：

| 枚举名 | 枚举值 | 说明 |
|---|---|---|
| `Enum.TextVerticalAlignment` | `Top` | 顶部对齐 |
| `Enum.TextVerticalAlignment` | **`Middle`** | **垂直居中** |
| `Enum.TextVerticalAlignment` | `Bottom` | 底部对齐 |

水平同理：`Enum.TextHorizontalAlignment` = `Left` / **`Middle`**（水平居中）/ `Right`。

**【推断】** MBS 那个「1」是**模拟器内部把名字映射成的序号**，
不是让创作者写进 Lua 的值。→ **写 Lua 时用 `Enum.TextVerticalAlignment.Middle`**，
不要去写数字 `1`。

- 官方同时提醒（§11 前言：「枚举系统」；另见 §10 `EnumItem`）：
  `EnumItem` 的字段是 `Name`（`string`，枚举值名称）/ `FullName`（完整名称）/
  `EnumType`（枚举类型名称），三者**均只读**。
  这与 MBS 的观察一致（「Enum 为 userdata；`==` 比身份；有 Name/FullName/EnumType」，
  `architecture.md:29`）。
