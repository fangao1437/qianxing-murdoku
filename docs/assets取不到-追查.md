## 二、官方规则（这部分第一版就是对的，保留）

全部取自 `【官方】《客户端控件API文档》`（本仓库缓存 `docs/api-cache/mhtakr07vej4.txt`）：

| 接口 | 官方原文 | 行号 |
|---|---|---|
| `game.GetClientUIRoots()` | 获取全部 UI 根控件。即**实际显示的客户端控件容器画布中的默认容器节点** | `:320` |
| `game.FindClientUIRoot(nodeName)` | 查找名称为 `nodeName` 的 **UI 根控件**（**只找根，不深搜**） | `:315` |
| `GetChildren()` | 获取**直接子控件** | `:1283-1285` |
| `GetChild(name)` | 获取当前控件中名称为 `name` 的**直接子控件** | `:1286-1290` |
| `FindChild(path)` | **按路径**查找子控件 | `:1291-1293` |
| `parent` | `ClientUIBaseControl`，**读写**，父控件 | `:1224-1227` |
| `active` | 只读，「`true` 时控件可见且挂载脚本逻辑运行，`false` 时控件不可见且脚本逻辑停止运行。**默认为 false**」 | §13 字段表 |
| `game.PrintClientUITree()` | 将当前客户端控件树**按父子层级写入日志** | `:170` |

`【官方】《客户端控件和客户端脚本》`：
> 客户端脚本只能获取到客户端控件的模板索引……**除客户端控件容器画布中的客户端控件以及客户端控件模板中的控件外，其他控件均为服务器控件，服务器控件无法被客户端脚本调用**。

**⇒ R1：没有任何官方接口提供"全树按名搜索"；脚本的可见宇宙 = `GetClientUIRoots()` 的根 ∪ 它们的后代。**

## 三、两条**新发现的代码缺陷**（都会让日志"什么都没打出来"）

文件：`lua/ui_controller.lua`，读取时 SHA256 前 16 位 **`63439179C4DB53FD`**（已复核，写这份文档时仍是这一版）。

### 缺陷 1：`_search` 调用在赋值之前 ⇒ 整段递归被静默吞掉

```
4188:  pcall(function()                          ← 大 pcall，吞掉一切错误
4199:    local _search = nil                     ← 只声明
...
4254:      local r0 = self.adapter:find("root")
4255:      if r0 == nil then return end
4256:      _search(r0, 0)                          ← ★ 调用时 _search 还是 nil
4257:    else
4258:      for i = 1, _rn do _search(_roots[i], 0) end   ← ★ 同样 nil
4259:    end
4260:    _search = function(node, depth)           ← 赋值在调用**之后**
```

真机 `_rn = 2` ⇒ 走 `:4258` ⇒ `attempt to call a nil value (local '_search')` ⇒ 被 `:4188` 吞掉。
代码注释 `:4194-4198` 自称已用"先声明再赋值"修好 —— **只做了声明在前，赋值仍在调用之后 ⇒ 没修好**。
**⇒ 这就是真机"递归一行『第N层看到』都没有"最可能的真凶。**

> ★ **顺带纠正 task-1 里的一条"实测事实"**：`root:GetChildren()` ✗ **返回空**。
> task-1 的原话是「`root:GetChildren()` ✗ **返回空**（**递归一行输出都没有**）」——
> **括号里那句才是唯一的证据**，而"递归一行输出都没有"**恰好是缺陷 1 的逐字症状**。
> ⇒ `【推测】` **那条"返回空"很可能是把缺陷 1 造成的空日志误读成了"测到空表"**，
> 而不是真的调用 `GetChildren()` 拿到了空表。
> 旁证：真机 `find("home")` ✓ 本身就要求从根起的 `GetChildren()` 递归成功（`find_in` `:294-300`）；
> `【模拟器】` 侧也直接反证（`容器节点 子控件=14`、`stage 树上 49 个子控件`）。
> **⇒ "GetChildren() 是引擎限制"与"GetChildren() 返回空"两条都不成立**，`GetChildren()` 是好的。

### 缺陷 2（★ 新发现）：清缓存那段在 `if _rn == 0` 里 ⇒ 真机永远不执行

```
4242:  if _rn == 0 then
4243-4248:  -- 注释：查调色板前先清一次名字缓存（为了排除负缓存）
4249:    if self.adapter ~= nil and not self._cache_cleared then
4250:      self._cache_cleared = true
4251:      ... self.adapter:invalidate_lookups("调色板查找前") ...
4252:    end
4253:    pcall(... find("root"):GetChild("assets") ...)
4254-4256:  ... find("root") ... _search(r0, 0)
4257:  else
4258:    for i = 1, _rn do _search(_roots[i], 0) end
4259:  end
```

`_rn == 0` 才是"一个根都没有"。真机 `_rn = 2` ⇒ **`invalidate_lookups` 与 `:4253` 那句"按名取 assets"整个被跳过**。

★★ **⇒ task-1 里"已排除：负缓存（加了 `invalidate_lookups` 仍失败）"这条前提不成立 —— 那个调用在真机上从未执行过，负缓存根本没被排除。**

> 注意：**负缓存解释不了 `GetChild("assets") = nil`**（`GetChild` 是引擎直调，不走适配器缓存）。
> 但 `:4217` 那句 `self.adapter:find("root")` **走缓存** ⇒ 若 `find("root")` 被缓存成"某个别的节点"，
> 后面所有基于它的判断都会跟着错 —— 这正好接上 §四 的假设 H5。

**两处修法（都是一行级，交给主项目）**：
1. 把 `:4260` 的 `_search = function … end` **整段移到 `:4242` 之前**（或两处调用加 `if _search then`）。
2. 把 `:4249-4253`（清缓存 + 按名取 assets）**移出 `if _rn == 0` 分支**，成为无条件执行的前置步骤。

### 4.0 ★ 官方文档里到底有没有"必须由编辑器创建"这一条？（诚实回答）

**没有原文。** 我把客户端语料与相关官方文档都查过了，**没有任何一句写着"必须由编辑器创建 / 手工写进存档的控件不生效"**
—— 官方文档不会讨论手改存档。但它有**三条已经文档化的规则**，合起来**指向**这个方向：

| 出处 | 原文 | 它说明了什么 |
|---|---|---|
| `【官方】《界面控件组》`（缓存 `docs/api-cache/mhg1700h8bug.txt:22-31`） | 「**界面控件组状态：激活、未激活**……**激活** → 存在于界面布局，可通过节点图管理表现状态；**未激活** → **不存在于界面布局**，不可操作表现状态」 | ★ **"未激活"的官方定义就是"不存在于界面布局"** ⇒ 一个控件组只有"激活"才**存在于界面布局**；**不在界面布局里的东西，运行时就是不存在** |
| `【官方】《界面控件组》`（同上 `:47-48`） | 「在界面布局中引用的界面控件组模板，**默认随界面布局一同激活**」 | 正常经编辑器进入界面布局的东西**自动**获得这个"存在"资格 |
| `【官方】《局内编辑器教程》`（缓存 `docs/api-cache/mhr6jorjp77a.txt:65`） | 「**界面控件组库中制作的类似元件库中制作的元件，实际游玩时并不显示，需要添加至界面布局中才会显示**」 | ★ **同一条规则的另一种说法**：不在界面布局里 ⇒ 游玩时不显示 |
| `【官方】《客户端控件和客户端脚本》` | 「**除客户端控件容器画布中的客户端控件以及客户端控件模板中的控件外，其他控件均为服务器控件，服务器控件无法被客户端脚本调用**」 | ★ **对客户端脚本而言，"在不在客户端控件容器画布中"就是能不能被脚本调用的分界线** |

**⇒ 三条规则合起来**：**"在界面布局里 / 在客户端控件容器画布中"是一个独立的、由引擎侧登记的资格，
不是"存档里长得像"就自动拥有**。工具把记录直接写进 `.gil` 时，**编辑器会把它画出来（编辑器读的是记录树），
但它没有被走一遍"编辑器创建 → 登记进界面布局/控件组"的流程** ⇒ 可能在运行时构建游玩态时不被实例化。

**⚠️ 但必须讲清楚**：这一段的**前两句是官方原文（有出处）**，
**"工具注入的记录因此不被实例化"是我的推理，不是官方结论** ⇒ 标 **`【推测】`（强）**。

### ★★★ H8（第 4 轮新头号假设；**机制已在代码里核对过**）：陈旧句柄 —— 命中缓存永不失效

**机制（`【代码】lua/engine_adapter_qianxing.lua`，本次逐行核对）**：

```lua
397: function Adapter:invalidate_lookups(why)
398:   self._misses = nil          -- ★ 只清【负】缓存
399:   self._subtree_dirty = true
400:   self._lookup_gen = ...
       -- ★★★ 没有 self.controls = {}  ⇒ 【命中】缓存一个都不清 ★★★
405: end

414: function Adapter:find(name)
415:   local hit0 = self.controls[name]
416:   if hit0 ~= nil then return hit0 end     -- ★ 命中就返回，**从不校验这个句柄是否还活着**
      ...
       -- 只有 drop_lookup(:410) 与 destroy_control(:3312) 才会清单个名字，
       -- 而 destroy_control 只对【脚本实例化的】控件生效（:3306，「编辑器手摆的只能藏起来」）
```

**而引擎侧**（`【官方】《客户端控件和客户端脚本》`）：
> **玩家传送、断线重连时，所有的客户端控件都会被销毁然后回到初始状态**
> 客户端容器控件**隐藏或销毁**时，客户端控件**销毁**

⇒ 只要发生过一次"控件被销毁重建"（传送 / 断线重连 / **容器隐藏再显示** / 重开关卡），
之前被缓存下来的句柄就**全部变成陈旧句柄**，而 `find` 会**照旧把它们返回**。

**这一条能一次解释两个症状，且不需要编辑器侧有任何异常**：

| 症状 | H8 的解释 |
|---|---|
| `find("root")` ✓「成功」 | 返回的是**陈旧句柄**，不报错，看起来就是成功 |
| `cached_root:GetChild("assets")` ✗ | 陈旧句柄底下什么都没有 |
| **`cached_root:GetChildren()` = 空** | ★★ **陈旧句柄的子控件列表就是空的** —— 这条第一次有了干净的、不需要假设编辑器有问题的解释 |
| `find("home")`/`find("modal")` ✓ | 它们是**独立的按名查找**；命中的那份缓存若是在**重建之后**建立的，就是**活句柄** ⇒ 取得到 |

**为什么"`modal` ✓ 而 `assets` ✗"不构成反证**：
现有证据**时刻不同、来源不同** ——
- `modal ✓` 来自**开局**的「常驻光标回读」那一次；
- `assets ✗` 来自**调色板查找**那一次（`ui_controller.lua:4221`）；
- 而 `left/tray/board/intro/select` 那一行**其实是模拟器日志**（我本次跑出来的），**不是真机** ——
  本工程的 `.gil`（218.1/219/222/214.3/217/215）里**根本没有这几个名字**
  （`node tools/qx/probe_gil_names.mjs` 实测）。
⇒ **两者不是同一次测量的对照**，不能用来否定 H8。

**H8 的可判据（已写进探针 §4）**：
把 **`adapter:find("root")`（走命中缓存）** 与 **`GetClientUIRoots()` 里那个根（引擎现给的活句柄）**
**在同一时刻**并排比：
