## 一、从 744 出发的二次瓶颈剖析

744 在严守 11 条历史禁区的前提下，已经将稳态 5 秒 API 调用压低约 80%。但在面向移动端的进一步高仿真 Profiling（基于真实 `.gil` 导出的 **8,578 个 UI 控件节点**，覆盖冷启动、四页面稳态、12 次连续切屏峰值、全页交互 7 大场景）中，发现 744 仍存在六大显著开销，几乎全部受制于 11 条历史禁区的“保守写法”：

1. **切屏峰值卡顿（受限于禁区 3）**：`Controller:_render_impl` 在任何同关切屏（首页 ↔ 选关 ↔ 商店 ↔ 背包）时都无条件调用 `invalidate_lookups`、`rearm_raycast`、`rearm_cursor`，强行丢弃全部有效控件句柄并触发多趟 8,578 节点全树 DFS 与全树射线重扫。连续 12 次切屏（`screen_switch_burst`）在 744 上仍消耗 **573 ms / 472,967 次 API / 2,381,997 次 `pcall` / 261,284 次 `GetChildren`**。
2. **每帧/热路径 `pcall` 粒度过细（受限于禁区 2）**：`index_in`、`enable_raycast`、`path_lookup_655`、`set_property`、`help_visible`、`sync_adapt715r`、`Tutorial:_visible` 等处对同一控件的 `name`/`visible`/`active`/`GetChildren`/`raycastTarget` 拆分成 2～5 个独立 `pcall(function() ... end)`，造成单次切屏 `pcall` 破百万次并产生大量短命闭包。
3. **关内 30 帧格子直遍历（受限于禁区 4）**：`Murdoku.on_update` 关内每 30 帧对全部格子反复执行 `find` → `GetChildren` → 嵌套 `GetChildren` → 逐属性 `pcall` 读回与无条件 `face:SetVisible(true)`，导致 `steady_level` 下 5 秒仍产生 **24,321 次 API / 20,289 次 `GetChildren` / 83,626 次 `pcall`**。
4. **每帧强制 `SetAsLastSibling` 与无意义显隐覆写**：`Adapter:on_tick` 每帧无条件 `art685.mark.overlay:SetAsLastSibling()`（300 帧 300 次），`sync_block640` 每帧对 `block640.*` 重复执行 10 次 `pcall` + 置顶，`Tutorial:_visible` 每帧对 `td.home/td.l1/td.l2` 执行 900 次 `noopVis`，非关内 `registration_clock >= 2` 每 2 秒对尚未实例化的 `cell.*` 重试 `bind_input` 触发 8,578 节点全树 DFS。
5. **非关内每帧冗余查找与历史废弃名**：`Levels.all()` 每帧重复加载并分配新表、`murdoku_vis_ids` 每帧循环查找 32 个控件、`CURSOR_CONTAINERS` / `TUT_PROBE_NAMES` / `key_control_fallbacks` 残留 `"board"` / `"left"` / `"tray"` / `"actions"` / `"select"` 等历史废弃名导致缺失探测反复退避。
6. **`sync_adapt715r` 乒乓双写与稳态重算**：`ADAPT715R_TARGETS` 中 `adapt715r.WAX.12` 与 4 个翻页器控件先写入旧锚点公式、紧接着在下一行被 `transform` / 专属公式覆盖，每次刷新产生双写抖动；且页面/画布/设备槽/确认条均未变化时仍按 0.25s 重算全表。

## 二、11 条禁区解禁策略与核心功能保障

745 解开 11 条禁区的“写法限制”，但**100% 保留每条禁区背后的功能与容错底线**：

| 禁区 | 历史写法限制 | 745 解禁优化手段 | 核心功能与兜底保障 |
|---|---|---|---|
| **1. `hex.back` 唯一返回入口** | 不改确认条与相关链路 | `sync_block640` 的 `confirm` 分支改为按 `pending` 变化驱动置顶，去掉每帧无效 `help_visible` | `hex.back` 事件、`back_confirm → exit_menu`、`submit/restart → pending` 确认条完整保留（专项 `zone1` 通过） |
| **2. 所有 `pcall` 包裹** | 逐属性拆分、不敢合并 | 合并同一控件连续读/写/取子操作为单次静态无闭包 `pcall`（`p745_index_node`/`p745_ray_step`/`p745_set_vis_guard`/`e745_transform`/`t745_set_vis`），并带降级回退分支 | 任何单个控件抛错均被捕获且自动降级，绝不中断主循环（专项 `zone2` 异常注入通过） |
| **3. 树遍历与跨帧缓存** | 切屏无条件全清缓存重扫 | 同关切屏先 O(1) 调用 `Adapter:_root_alive745()` 校验 `root.name == "root"` 且仍在 `GetClientUIRoots()` 中；存活则保留全部有效句柄，仅清 `_misses` 与标脏标记层；`path_lookup_655` 缓存根容器句柄并单 `pcall` 链式下钻；`enable_raycast` 单趟完成即收敛 | 换关或 `root` 句柄失效/重建时自动回退全量 `invalidate_lookups + rearm_raycast + rearm_cursor`（专项 `zone3` 销毁重建后 `gen 1→2` 通过） |
| **4. 关内 30 帧 `face` + `x` 70%** | 每 30 帧重新 `GetChildren` 树遍历并无条件写 `face:SetVisible(true)` | 按 `_lookup_gen` 缓存每格 `{cell, box, face, x}` 句柄；合并单格校验为单次 `pcall(sync_cell745)` + 读回守卫；连续 2 趟 0 修正后自动降频至 120 帧兜底，一旦修正或句柄抛错立即恢复 30 帧 | 仍恒亮 `face`、仍强制 `x = 0.7 * cell`；实测外力篡改 `face.visible=false`、`x=120x120` 后自动修复至 `true` 与 `84x84`（专项 `zone4` 通过） |
| **5. 单射末次写入权** | 保留原流程 | 仅去除 `_grid_refill_now` 与 `_grid_disable_gray_raycast` 中的匿名闭包与冗余写 | 单射两趟（早期 + 末次）写入权完全不变 |
| **6. `_grid_base` 永不重置** | 不触碰 | 保持不变 | 索引基准行为 100% 兼容 |
| **7. `RefreshItems` 不清签名** | 不触碰 | 保持不变，删去 `_grid_render` 中已失效的诊断空转循环 | 保留滚动条位置，不回顶 |
| **8. `gray` 关射线与交互** | 3 次独立 `pcall` 赋值 | 合并为单次 `pcall(c745_disable_gray, cg)` + 写前判等守卫 | `raycastTarget/blockRaycast/interactable` 全关，不抢点击 |
| **9. `ensure_cells` 格子几何** | 不删任何 `SetSizeDelta`/`SetAnchoredPosition` | 完整保留几何写入，仅在 `select_render_content` 加写前读回守卫 | 格子与 `note`/`x`/`face` 几何位置不变 |
| **10. 图片 `SetImage`/文字 `SetText`** | 不统一成属性赋值 | 完整保留 `SetImage` / `SetText` 调用链 | 兼容千星控件渲染机制 |
| **11. `_row_face`/`_row_letter`** | 保留数据通道 | 完整保留，仅对 `Tutorial:_find/_visible` 加读回守卫与零闭包 | 头像/标记/教程单射通道不变 |

## 六、局限说明与真机验收建议

- **测试局限**：以上结果均来自基于真实 8,578 节点 `.gil` 结构的离线高仿真模拟，尚未导入千星奇域真机实测。
- **建议真机必测 5 项**：
  1. 首页 ↔ 选关 ↔ 商店 ↔ 背包快速连续切屏 10 次，验证体感无卡顿且无页面残留；
  2. 进入第 1 关，验证棋盘底图 `face` 全部正常点亮、划 `X` 大小保持 70% 且始终位于头像/标记之上；
  3. 点击左上角 `hex.back` 弹出退出菜单、点击提交/重开弹出 ✓/✗ 确认条，确认返回和取消链路正常；
  4. 线索卡列表滚动、点击选人放格与 `gray` 灰白层不抢点击；
  5. 手机端切换分辨率/切后台重连后观察控件树重建自愈是否正常。
