# 715 背景漏边与黑底深度调研

截至 2026 年 11 月 18 日。研究对象：原始715、v2、v3、v11、v12及用户本轮两张截图。

**核心发现：v12存在已复现的布局所有权冲突。控制器先把root写成中心锚点、固定1600×900，适配函数随后要求root必须满拉伸且SizeDelta接近零，不满足便直接返回。这个返回同时阻断背景缩放和页面底色显隐。v2没有该门槛，且保留原服务器背景。**〔L1–L4，E3〕

本轮完成调研与隔离诊断，未修改运行时、构建器或任何GIL，未生成v13，也未操作游戏。代码级冲突已证实；截图的完整引擎渲染和初始化时序尚未实机回放，不能宣称唯一根因已完全锁定或问题已经修复。

## 一、证据与现象

- 用户本轮提供的主页截图为1604×1260，包含窗口标题栏；识别结果显示上下露出游戏天空、草地，主体大面积近黑色#130E0B。附件image.png同样为1604×1260，选关页木板图案仍在，上下仍露世界。整个截图尺寸不能直接当UI画布尺寸。〔U1〕
- 用户确认v2曾实现上下适配；此前确认v3移动端左右不漏，但4:3、16:10上下有问题。这些作为实机对照事实保留，不扩大为v2或v3已通过所有设备。〔U2〕
- 本轮直接读取5个GIL，不经模拟器转换，核查外层宿主、root、背景及选关底色。又执行真实导出Lua中的属性设置函数与适配函数，检查运行顺序造成的冲突。〔E1–E3〕

证据标记：〔U〕用户截图或观察；〔L〕本地源码定位；〔E〕本轮执行结果；数字引用为本轮打开的网络资料。源码位置相对qianxing-murdoku。

## 二、为什么v2能继续适配，而v12会停住

### 2.1 已确认的调用链

1. ui_controller的设计尺寸为1920×1080，默认换算尺度为5/6。〔L1:3567〕
2. 控制器为root输出全设计尺寸rect，并设置pos_runtime=true。〔L1:4702〕
3. 渲染器遇到pos_runtime后，将adapter.runtime_rect.root设为true，再下发rect。〔L1:7173〕
4. Adapter:set_property因此绕过respect_editor_rect保护；通用rect分支把root锚点改为(0.5,0.5)至(0.5,0.5)，尺寸写为1600×900，位置为(0,0)。〔L1:13513、13590〕
5. v12的sync_adapt715r要求root尺寸差接近(0,0)、锚点(0,0)至(1,1)、单位缩放及中心pivot。真实属性设置函数刚写出的根不符合，函数打印root-transform-pending后return。〔L2:66、86〕
6. 页面背景开关、底色换色、完整背景cover、选关底纹和卡片缩放都位于这个return之后。只要根保持上述状态，重复调用仍会退出。〔L2:104、119、186、202〕

**这不是尚未证实的API尺寸语义问题，而是两段项目代码直接要求同一根节点具有互不兼容的几何状态。**〔L1、L2、E3〕

### 2.2 隔离执行结果

实验从各版本导出Lua提取原始Adapter:set_property和sync_adapt715r，控件API使用内存替身。输入为Keyboard、API画布1600×1200，按控制器已确认的runtime_rect.root=true执行root的1920×1080矩形写入，再按home→select→home调用适配函数。没有改写被测函数。〔E3〕

| 观察项 | v2 | v12 |
|---|---|---|
| 原属性函数写入后的root | 1600×900，中心锚点 | 1600×900，中心锚点 |
| 选关底纹倍率 | 三次均为1.333333 | 未执行该倍率写入 |
| 根状态报告 | 无阻断 | 三次均为root-transform-pending |
| 背景页面管理 | 不由这一适配函数承担 | 被根校验一并阻断 |

此实验验证真实函数之间的冲突，未执行完整控制器、引擎绘制与触控。v2并没有v12新增的客户端完整背景，不能把实验替身中的同名背景状态当作v2实物。〔E3〕

### 2.3 v2值得参考的具体内容

v2选关底纹独立使用max(1600/1600,h/900)，其中h=1600×API高/API宽；当API正确报告4:3时，底纹可达到1200设计高度。它没有root_ready阻断，因此通用布局写过root之后仍会执行。v2原服务器背景记录与原始715逐字节相同。〔L3:15654、15687；E1〕

这支持保留v2“原背景路径与按钮布局分开、选关底纹独立适配”的思路；不支持直接整版回退。v2仍含移动端API恰为1600×900时按720高处理的历史兜底，不能推广到所有平板。服务器背景在实际引擎中如何映射到不同屏幕，不能仅凭固定1600×900存档尺寸推断。〔L3:15658；U2〕

## 三、近黑背景从哪里来

### 3.1 没有发现图片整体被改黑

v12导出常量HOME_COLOR=4290136608，对应ARGB 0xFFB64A20；SELECT_COLOR=4279438859，对应0xFF130E0B。截图近黑色恰好吻合选关底色，而不是原警局底色。〔L1:16825；U1〕

本轮对v12的646个图片图元逐个比较服务器源31/4颜色、31/2资源与客户端84/502颜色、84/503资源，发现0项不一致。其余3项是文字，不在这个图片字段比较内；没有据此宣称字体、遮罩和所有组件属性均正确。原素材组及649个源叶层在五个版本的编码摘要一致。〔E1〕

### 3.2 v12新增了可跨页面覆盖的深色层

v2选关底色位于选关子树：root/art641.select/art642.select.backdrop/grp653.static.1.art642.select.backdrop/art647.select.bg.base。

v12把它移为root的直接子节点，排列在background.fill、完整background之后，因此具备覆盖完整背景的层序条件；尺寸改为随root拉伸加4个单位，颜色为#130E0B。该节点被加入DECOR，通用hide_unlisted会跳过它；页面隐藏由适配函数负责。〔L4:190、206；L1:11027；E1〕

根校验若阻断页面管理，选关底色不能按当前页面纠正。若它此前为可见，便可能在主页遮住警局背景；若OnInit已成功把它隐藏，则不一定出现同一黑底。因此，**已证实的是失效机制与覆盖条件；截图是否正由该节点覆盖，仍需实机读回节点visible、active、activeInHierarchy和初始化时序。**不能仅凭颜色相同认定唯一原因。〔L2:119、202；E2–E3〕

v12同时把服务器背景四端缩放设为零，失去了v2保留的那条显示路径。这里的“服务器背景”指服务器控件层中的素材引用，不是要求改用千星沙箱节点图。〔L4:188；E1〕

## 四、为什么原生拉伸仍然漏上下

**拉伸填满的是直接父容器，不等于物理全屏。**本地MiliUI实测缓存记载：子控件锚点相对直接父级，父缩放影响子级尺寸与偏移；拉伸轴的SizeDelta不等于最终可见尺寸。官方API说明层级共同影响变换、可见性与裁剪，并只把GetUICanvasSize定义为UI画布宽高。〔L5:37〕[7]

v12底色即使保持满拉伸，也跟随运行时被固定为1600×900的root；若实际可见区域更高，底色无法仅靠“满拉伸”覆盖父容器以外区域。具体露出多少、是否另有裁剪，仍取决于引擎映射。〔L1、L2；工程推导〕

本轮独立读回的外层客户端容器ID为1073741845，通过组件73/501引用root ID 1073741846。root没有普通parentId，普通父链遍历会在root停止，不能据此说已经核查了外层宿主。外层容器在原始/v2/v3/v11/v12中的编码摘要前20位均为96df4a1be24deb146137。四端参数相同：min=(0,0)、max=(1,1)、position=(0,0)、sizeDelta=(-0.000244140625,0)、scale=(1,1,1)、pivot=(0.5,0.5)。这排除了“这几版修改了外层容器存档几何”的解释；它不证明运行时没有原生安全边距。〔E1〕

MiliUI当前KNOWN_ISSUES提到PC手柄可能有原生安全边距，作者尚未做统一补偿。本问题不能直接归因于它，尤其用户截图未给出实际GetDevice读回。官方适配说明区分PC、移动、主机、移动手柄四类设备，要求分别设置，并支持拉伸锚点。[8][34]

## 五、上轮924项检查为什么没挡住问题

- v12审计明确测试执行适配函数、预设宿主宽1600且高度随API比例变化，没有完整执行控制器的动态内容生成。因此没有覆盖“控制器先改root，再执行适配”的集成顺序。独立适配函数通过，不能推导完整更新链通过。〔L6:4、15；E3〕
- 测试把API与宿主比例绑定，无法发现两者口径不同。反例：假定API仍为1600×900、实际宿主1600×1200，v12计算cover=1，1600×900美术相对宿主少300高度，即居中时每边150设计单位。这只是反例模型，不是截图测量，也不表示常驻底色一定没覆盖。〔E2〕
- set_visible只依据pcall未报错，不读回visible/active。注入缺少方法或GetChildren失败后，实验日志仍出现visibility_ok=true，而649个初始化为不可见的替身叶层仍未点亮。这证明“成功日志”存在假阳性，不能证明实机缺方法。〔L2:123、139；E2〕
- gil_to_save会重建sc1外层，boxes计算只取KEYBOARD。该工具可用于辅助预检，不能替代原始GIL宿主核查或四端引擎测试。〔L7:577、606〕

## 六、建议修复顺序与最小验收

以下为下一轮实施方案，本轮未执行。

1. **先统一root的布局所有权。** 选项A是保留公共root原生满拉伸，不再让通用控制器对它输出固定rect；选项B是保留固定内容root、另用真正随宿主变化的背景根。A涉及现有内容坐标，B涉及重挂与显隐，两者都须验证按钮命中，不能只删除root_ready就宣称完成。〔工程建议〕
2. **页面显隐独立于几何校验。** 根数据暂未就绪时也必须能关闭异页底色；明确默认隐藏、页面切换及失败重试。优先让选关专属底色归选关页面管理，避免仅靠单个适配函数维护公共根上的不透明层。〔工程建议〕
3. **用v2作背景A/B基线。** 保留当前按钮适配；隔离验证原服务器背景与客户端重建背景，逐次只变一条显示路径，不同时打开两套背景作为正式兜底。先确认v2在同设备同窗口同页面的上下覆盖，再决定背景路径。〔U2；工程建议〕
4. **先验证完整顺序，再算cover。** 测试必须覆盖控制器render→Adapter:set_property→原页面显隐→sync_adapt715r，包含OnInit/OnStart、home→select→home→game，重复刷新与句柄代际变化。至少检测运行时root尺寸、锚点和实际页面状态。〔工程建议〕
5. **覆盖、构图、内容缩放分别验收。** 底色填满、装饰图完整覆盖、纸张与卡片同步、按钮命中是四项不同检查，不能以其中一项替代其余。〔工程建议〕

最小实机证据：记录GetDevice、GetUICanvasSize、root锚点/SizeDelta/缩放、background与selectBase的active/activeInHierarchy/visible、fill.imageColor、页面、背景叶层可见数量；记录点放在控制器render前后和适配函数返回前。当前代码在root校验失败时只写一句pending，后面的geometry日志也被跳过，这不足以定位。日志应去除账号等个人信息。〔L2:92、254；工程建议〕

## 七、本轮交付与边界
