## §1 一句话

按用户指定路线：用**仓库里那个"兼容千星的外部图片网站"**——`github.com/1475505/Miliastra-toolbox-primitive-shape`
（在线地址 `https://qx-img.070077.xyz`，千星奇域拼图工具）的**本地引擎**把原作家具图拟合成图元，
导出**结果文件**（`.lua`：`PALETTE` + `ELEMENTS` 记录），再从结果文件**拆出"正确拼法"**
（图元类型 / 中心 / 宽高 / 旋转 / 每图元 RGBA），换算进存档数据 `lua/furn_art_records.lua`，
最后在游戏里由适配层**逐图元运行时实例化**图片控件画出来（一件家具 151~200 个控件 —— 这是模板层数不可能装下的量）。

## §2 链路（可复跑）

```
原作图标（_work/art-ref/render/icons-colored/*.png，RGBA 透明底）
  ↓ ① 拟合（工具本地引擎，PNG 模式、只允许圆形/椭圆、N=160~200）
工具结果文件（_work/art-work/fit/<kind>-n<N>.lua：PALETTE + ELEMENTS）
  ↓ ② 拆解（_work/art-tools/gen_art_records.py）
    · 记录换算到"格子"：{imageId, w, h, dx, dy, rotDeg, colorARGB}
    · 丢掉工具用来**铺底/光晕**的图元（比整件还大、或低透明度大块）——搬到格子里是一圈脏光晕
    · 长桌：用**方桌的拟合结果**沿长轴做"位置+尺寸双拉伸"得到横/竖两套独立数据
      （直接拟合拉伸图会得到一堆奇怪椭圆，实测更糊）
  ↓ ③ 生成 lua/furn_art_records.lua（7 组、1174 条图元、76 KB）
  ↓ ④ 运行时绘制（适配层 `Adapter:_paint_furn_art`）
    每格 N 个图片控件：SetImage(StaticReference,100001/100002/100003) + imageColor(ARGB)
    + SetSizeDelta(w·格, h·格) + SetAnchoredPosition(dx·格, −dy·格) + SetLocalRotation(0,0,rot)
    父级 = 格子 `content/furn`（502 新增，层序在 obj12 与 x 之间 ⇒ 压地板、但不压墙/门/笔记/头像）
```

**为什么必须"运行时实例化"**：一件家具 151~200 条图元，格子模板只有 12 层；而千星客户端 API 支持
`game.InstantiateClientUIControl(prefabIndex, parent)`（拼图工具自己导出的 Lua 运行时就是这么画的），
`502` 里的 `tpl.prim`（「仅存为模板」= 模板源孤儿记录 + 母本）提供 `prefabIndex = 1073746302`。

## §5 未验证 / 风险（真机前必看）

1. ★ **`InstantiateClientUIControl` 真机未验**：`tpl.prim` 的模板源是**按仓内真机验证过的模板模型同构复刻**（孤儿 + 母本 + 族号），
   但新模板本身没上过真机。失败症状：**家具完全不见**（实例化返回 nil）。回退命令 integrator 已给：`--family=79` / `--guid-base=1073746400`。
2. **控件量**：一颗棋子最多 ~1257 个图元控件（第二关 6 格家具 × 150~200 条），全部是运行时实例化。
   `furn_prim_cap = 260` 是**每格**上限；如真机掉帧：先把 `plant/shelf` 的拟合条数降到 120（改 `_work/art-tools/gen_art_records.py` 的 PLAN 重生成）。
3. **观感上限**：工具是"椭圆拟合"，形体圆润的椅子/植物/书架/雕塑效果明显好（已对照工具预览）；
   **桌子是直角+长边，椭圆拟合会糊**，所以桌子保留手搭 6 层（黑描边/桌面/桌沿/两腿头），地毯同理。
4. **旋转方向**：`SetLocalRotation(0,0,rotDeg)` 直接照抄工具运行时（它已在千星跑通）；离线预览按"PIL 正角"验证过方向一致。
5. **坐标口径**：工具记录 `cy = −（自上而下像素 y）`；换算后 `dy` 与存档既有家具数据同为"向下为正"。
