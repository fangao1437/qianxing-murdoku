# 回执 —— `things` 是怎么建出来的，以及"控件被运行时创建"的根源（2026-10-18）

> 用户结论（本轮确认）：「控件被运行时创建的**起点**就是基于 `395` 建了 `things` 的 **396**，根源在这」
> 本文把第一轮建 `things` 的**全部做法**逐条写出来（可复现），并说明它为什么必然引出
> 「运行时创建控件 → 反复试玩必撞 GUID」这条后果链，以及后来每一版各自修掉了哪一段。

| 项 | 内容 |
|---|---|

| 埋下的三颗雷 | ① 克隆控件**只改了顶层 `#501`**，`/#502/#11/#501`、`/#505/#503/#504/#4` 仍指母本 ② 规划里另有 4 个 `obj.*`（父 `assets`，名字与存档里的 6 个**不同**）⇒ 渲染循环判"计划有、存档无" ⇒ **真的建**，每次试玩 +4 ③ `content/obj` 克隆自 `face`，同雷① |

## 三 396 的完整做法（可复现）

```bash
node tools/gil/gen_things_obj.mjs --in=395.gil --out=396-things.gil
# 产出：354 条记录 / 1,601,546 B
```

### 目标结构

```
canvas root (#1073741846)
├── …（原有 200 多个控件不动）
├── things            ← 新增：素材区容器（画布外 200000,200000 / 900×180）
│   ├── obj.table     ← 新增：6 个图片控件，名字 = 脚本引用键
│   ├── obj.plant
│   ├── obj.carpet
│   ├── obj.chair
│   ├── obj.shelf
│   └── obj.statue
└── cell 模板（#1073741876）→ content（#1073741888）
    └── face / hint / **obj** / x / wall.* / note / door.*   ← 新增 obj（第 2 位）
```

### 逐步做了什么

| 步 | 动作 | 细节 |
|---|---|---|
| 1 | **克隆容器** | `things` = `cloneField(tpl-container 的 #505)`，改名 `tpl-container → things`，新 id = `maxId + 1` = **1073742786** |
| 2 | **补父指针** | `tpl-container` 是**根级记录、没有 `#504`** ⇒ 新记录必须补：`{ field: 504, num: parentId }`，插在 `#505` **之前**（保持字段顺序与其它记录一致） |
| 3 | **挪到画布外** | 四个状态块的 `pos`（`#504` 对）写成 `200000, 200000`、`size`（`#505` 对）写成 `900×180` —— 与既有 `tpl-container` 同一套路，画面上看不见 |
| 4 | **6 个素材槽** | 每个都从 `tpl-container` 克隆（保持"容器/图片"能用的类型），改名 `obj.<kind>`，id 依次 1073742787…1073742792，`size = 135×135`（设计单位 = 画布 108 = 格子边长），补一个**图片块**：`imageId = 100001`（白色矩形）、`imageType = 1（Stretch）`、`imageColor =` 各自的占位色 |
| 5 | **占位色表** | `obj.table 0xFFB07946` / `obj.plant 0xFF4CAF50` / `obj.carpet 0xFFD9C8A6` / `obj.chair 0xFFE0A040` / `obj.shelf 0xFF7A5230` / `obj.statue 0xFFB8B8C0` |
| 6 | **登记子列表** | `things` 原本没有 `#503` 子列表 ⇒ 新建空的，再用 `setChildList()` 写进 6 个子控件的 id（`asIdList/setChildList` 是仓库工具里的标准写法） |
| 7 | **格子图层 `obj`** | `content/obj` = `cloneField(content 下的 face #1073741889)`，改名 `face → obj`，新 id **1073742793**，`135×135`、白色 `0xFFFFFFFF`、`imageType=1`；插入 `content` 子列表**第 2 位**（`face, hint, obj, x, wall…`），并 `splice` 进字段树 |
| 8 | **写回与验收** | `writeGil()` 自带四道闸门：重读磁盘 / 往返逐字节一致 / 记录数 = 346+8 = **354** / 结构断言（父指针、子列表、`obj` 在第 2 位） |

### 当时"以为"做对的点（其实是雷）

| 当时的判断 | 实际情况 |
|---|---|
| "新 id 用 `maxId + 1` 就不会撞" | 只对**本档**成立；编辑器还会把**运行时创建**的控件也算进来（见雷②） |
| "克隆后改 `#501` 就是换了 GUID" | ✗ `.gil` 里 GUID **存三处**：`/#501`、`/#502/#11/#501`、`/#505/#503/#504/#4`（后两处是"又一份"和"反向引用"） |
| "存档里建好就不用脚本管了" | ✗ **规划里另外还有 4 个 `obj.*`**（见雷②），它们才是被运行时创建的 |

## 四 三颗雷（这才是根因链）

### 雷① 克隆控件 GUID 只换了一半（导入就会撞）

`_probe_innergids.mjs` 在 `402`（未修版）上的实测：

```
#1073741889 → face ＋ obj ＋ obj.table/plant/carpet/chair/shelf/statue
              路径：/#501、/#502/#11/#501、/#505/#503/#504/#4
```

- `content/obj` 是我从 `face` 克隆的 ⇒ 它带着 **`face` 的 GUID**
- 6 个 `obj.*` 也从同一母本克隆 ⇒ 都带 `face` 的 GUID
- ⇒ 编辑器看到"多个控件同一个 GUID" ⇒ 报「GUID 重复」

★ 为什么早期探针说"0 重复"：那些探针只看**顶层 `#501`**（`bigIdTop` 读的那一处）。**顶层的确实没重复**，但编辑器读的是另外两处。

★ 修法（v259）：`tools/gil/remap_ids.mjs` —— 把克隆体里**所有等于母本 GUID** 的 varint 改成它自己的（396/397 那批共 **62 处 / 9 个控件**）。

### 雷② 规划里另有一份 `obj.*`，它们**真的会被运行时创建**（反复跑必撞）

`ui_controller.lua` 里原本有一段 `OBJECT_PALETTE`：

```lua
local OBJECT_PALETTE = {
  ["obj.shelf"]  = 111051, ["obj.case"] = 111064,
  ["obj.desk"]   = 111050, ["obj.carpet"] = 106053,
}
for pid, pimg in pairs(OBJECT_PALETTE) do
  nodes[#nodes + 1] = { id = pid, kind = "button", parent = "assets", visible = false, … }
end
```

它和存档里的 6 个槽**对不上**：

| | 规划（脚本） | 存档（396 里我建的） |
|---|---|---|
| 容器 | `assets` | **`things`** |
| 名字 | `obj.shelf / obj.case / obj.desk / obj.carpet` | `obj.table / obj.plant / obj.carpet / obj.chair / obj.shelf / obj.statue` |

⇒ 渲染循环逐条判断"计划有、存档没有、**有创建路**" ⇒ `adapter:create_control(n)` **真的建**：
**每试玩一次 +4 个控件**，GUID 由引擎分配 ⇒ 累积到编辑器校验里就是"重复"。这就是「多次运行必撞 id」。

★ 用户日志的原文证据（v260 那次运行）：

```
[murdoku] 规划里有 35 个控件是【已知不需要】的（旧线索卡 / 旧滚动条 / board / left / legend / select / tray / room.* / obj.*） —— 按 info 打，不再当错误
```

`obj.*` 就在这份"计划里有"的名单里 ⇒ 它们一直在被尝试创建。
对照另一条日志（同一份存档第二次进关）：`棋盘格子：25 / 25 存在（本次新建 0 个）` —— **格子**是模板实例化、幂等；而 `obj.*` 不是。

★ 修法（v261）：**整段删除** `OBJECT_PALETTE` 的 push ⇒ 规划里 `obj.*` = **0 个**
（`dump_layout` 并集控件 **217 → 213**），素材只从**存档 `things`**（编辑器换图）或 `cfg.obj_art`（兜底）取。

### 雷③ `content/obj` 也是克隆（与雷①同一处病）

`content/obj`（两份模板各一个：#1073742793 / 1073742794）同样残留 `face` 的 GUID。
它不影响"素材区"，但会让编辑器把**格子模板**也判成重复 ⇒ 修法与雷①相同（`remap_ids` 覆盖 `obj`）。

## 六 下次建存档控件的正确做法（8 条清单）

1. **先备份 + 先只读核对**：`inspect_gil` / `_probe_kids` / `list_names`，确认要建的名字**确实不存在**。
2. **id 取号**：`maxId + 1` 起步，**并且**留足余量（建议 `maxId + 1000`），避免与"编辑器之后自己创建"的号撞。
3. **克隆后必须"全量改号"**：`/_501`、`/#502/#11/#501`、`/#505/#503/#504/#4` 三处都要改成自己的 ⇒ 直接用 `remap_ids.mjs`。
4. **父指针与子列表成对**：新记录要有 `#504`（父）；父的 `#503` 里要有它，且顺序就是层序。
5. **别让"规划"和"存档"各有一份同名控件**：脚本的 `push` 列表 = 规划；存档 = 真实控件。
   ★ 规则：**规划里只写"存在于存档"的控件**；素材这类"要新建"的东西，只在存档里建一次。
6. **确认哪些节点"有创建路"**：`ui_controller` 的渲染循环会对"计划有、存档无"的节点调 `create_control`；
   凡是放在规划里、又没进存档的名字，都会在**每次试玩**被重建一次。
7. **四道验收**：`roundtrip`（往返）、`check_names`（名字对账）、`_probe_dupids`（顶层重复）、
   **`_probe_innergids`（"同一 id 被两条以上记录使用"—— 这才是编辑器说的重复）**。
8. **跑两次再交付**：连续试玩两次，对比"控件清单"（`inspect` 里的名字/数量）——
   **第二次若多出控件，就是有人在运行时创建**。
