# 环境问题诊断记录（pwsh 无法启动 · 0xC0000142）

> 记录时间：2026-09-22 会话内。因为当时**所有 shell 都不可用**，本文是用
> 文件系统证据（DSH 实现代码 + 目录存在性探测）反推出来的，不是跑诊断命令跑出来的。
> 每条结论都标了「已实证 / 候选假设」。

---

## 1. 现象

| 项 | 内容 |
|---|---|
| 表现 | 每条 `pwsh` 工具调用都返回 `[exit code: 3221225794]`，且没有任何 stdout/stderr |
| 退出码 | `3221225794` = **`0xC0000142` = STATUS_DLL_INIT_FAILED** |
| 语义 | 进程**已经被创建**，但在**加载/初始化自己的 DLL** 阶段就失败了。（不是"找不到文件"，那会是 ENOENT） |
| 起始时间点 | 会话前 8 条 pwsh 命令**全部正常**；**第一条枚举 `BeyondAssets` 目录的命令立刻失败**，此后每一条都失败 |
| 影响 | 无法启动原神、无法运行 Lua 自检、无法打包/搬移文件（所以只能用目录分类代替 zip） |

那条"第一枪"命令是：

```powershell
Get-ChildItem -Force 'D:\新建文件夹\miHoYo Launcher\games\Genshin Impact Game\BeyondAssets' | ...
```

而它紧邻的上一条（枚举**上一级**游戏目录）是**正常返回**的。
`BeyondAssets` 里放着 `HoYoKProtect.sys`（原神内核级反作弊驱动）与 `BeyondAssistEditor/*.dll`（含 `0Harmony.dll`）。

---

## 2. 已实证的事实

### 2.1 DSH 到底启动哪个 PowerShell（读实现代码得到）

`DSH Desktop/resources/app/lib/windows-pwsh-sandbox.js`：

```js
return [join(programFiles, "PowerShell", "7", "pwsh.exe"),
        join(systemRoot, "System32", "WindowsPowerShell", "v1.0", "powershell.exe")]
       .find((candidate) => exists(candidate));
```

`node_modules/@deepseek-ai/dsh-pwsh-local/lib/index.js`：

```js
const candidates = [join(programFiles, "PowerShell", "7", "pwsh.exe")];
// ... 否则
return "pwsh";      // ← 退化为 PATH 解析
```

同文件里还有一句注释：**"avoid PATH-resolved portable pwsh"** —— DSH 自己就把
"PATH 解析到的 portable pwsh"标注为要避免的坑。

### 2.2 本机 PowerShell 的实际情况（目录探测得到）

| 探测 | 结果 |
|---|---|
| `C:\Program Files\PowerShell`（PS7 标准安装位置） | ❌ **该目录不存在** |
| `C:\Program Files (x86)` 全盘 `**/pwsh.exe` | ❌ 一个都没有 |
| `C:\Users\18182` 全盘 `**/pwsh.exe` | ❌ 一个都没有（也没有 Store 版的 pwsh 别名） |
| `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe` | ✅ **存在**（Windows PowerShell 5.1） |

### 2.3 由 2.1 + 2.2 推出的结论

**本机没有 PowerShell 7。** 所以：

- DSH **不可能**在跑 PS7；
- 会话早期那些正常返回的命令，跑的必然是 **Windows PowerShell 5.1**；
- 因此这不是"DSH 找不到 pwsh"，而是 —— **一个本来能正常启动的 PowerShell 进程，现在起不来了**。
  问题出在**进程环境**，不在"可执行文件是否存在"。

## 3. 候选成因（尚未最终定案）

### 假设 A：安全软件 / 反作弊拦截（与时间点最吻合）

本机同时装着 **360 全家桶**（`360Safe` / `360TotalSecurity` / `360Quarant`…）与
**米哈游反作弊**（游戏目录里的 `HoYoKProtect.sys`）。第一条去**递归枚举**
`BeyondAssets`（反作弊驱动 + Harmony DLL 所在目录）的命令触发拦截后，
之后每一次进程创建都失败 —— 完全符合"AV/EDR 挂钩进程创建 → 新进程 loader 初始化失败"的表现。

**判定方法（可复现实验）**：
1. 重启电脑 / 重启 DSH Desktop，先确认 `pwsh -Command "echo ok"` 正常；
2. **单独**跑那条递归枚举 `BeyondAssets` 的命令；
3. 若 `pwsh` 立刻再次全挂 → 假设 A 成立。

### 假设 B：本机资源 / 宿主状态

桌面堆或句柄耗尽、或 DSH 在我这条会话进行中被更新/重启导致派生链失效
（`DSH Desktop/crash-evidence/active-run.json` 显示当前 run 起于
`2026-09-22T17:20:11.851Z`，`pid 39284`，`version 2.0.13`；而
`AppData\Roaming\DSH Desktop\lib\windows-pwsh-sandbox.js` 的沙箱路径还会通过
Electron 以 Node 模式再起一层 runner，链条比一般 spawn 长）。

**判定方法**：重启 DSH Desktop 后，**不碰游戏目录**连跑 20 条以上命令；
若全部正常 → 假设 B 成立（或至少清掉了这一层）。

## 4. 建议的处理顺序（代价从小到大）

1. **重启 DSH Desktop**（最便宜，先做）。之后让我复测一句 `pwsh -Command "echo ok"`。
2. 仍失败 → **装一个正式版 PowerShell 7**：`winget install --id Microsoft.PowerShell`
   （或官网 msi）。这样 DSH 的解析会命中 `C:\Program Files\PowerShell\7\pwsh.exe`，
   顺带绕开 DSH 自己都标注过的"PATH 解析 portable pwsh"隐患。
3. 装了还失败 → 把 **DSH Desktop** 与 `powershell.exe` / `pwsh.exe` 加入 **360 信任区**，
   并确认测试时原神与反作弊驱动不在运行；翻一下 360 的拦截日志有没有 PowerShell 记录。
4. 可选（需要你改宿主配置）：在 DSH 里**显式指定 `pwshPath`**，例如指向
   `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`。
   依据：`windows-pwsh-sandbox.js` 在找不到 PS7 时**本来就会回退到 5.1**，说明显式配置是被支持的。
5. 复现实验（用于确认假设 A）：单独重跑
   `Get-ChildItem -Recurse 'D:\新建文件夹\miHoYo Launcher\games\Genshin Impact Game\BeyondAssets'`。

# 附：2026-09-24 千星沙箱踩坑记录（控件可见性 · 文本外显）

> 这一天的排查绕了很多弯路，把所有结论固化成清单，避免重犯。

## A. 「控件加进去了但画面上看不见」——先怀疑"透明叠加"

| 层 | 控件 | 本身画东西吗 | 说明 |
|---|---|---|---|
| 1 | 客户端控件容器 | ❌ | 透明画布，唯一作用是让里面的客户端控件能显示 |
| 2 | 容器节点（`board`） | ❌ | 官方："容器节点主要作为其他客户端控件的挂点" |
| 3 | 预设按钮（`cell.1.1`） | ❌ | 必须配「按钮状态节点」外显样式才看得见 |
| 3′ | 文本框 | ⚠️ | 看内容 / 对比度 / 大小 |
| 3″ | 图片 | ✅ | **验证链路时用它最省事** |

**给预设按钮配外观（官方三步）**：在按钮**下面**加子控件（图片/文本框）→ 选中按钮 →
【基础】→ 按钮设置 → **按钮状态节点** → 把子控件**拖到【默认】节点上**
（或**单击【默认】节点**在弹出列表里勾选）。四种状态：默认/悬停/按下/不可用。
配好后**点状态节点的播放键**可在编辑器内预览。

**文本框看不见的三件事**：①对比度（默认纯白字 + 0% 透明背景，打在亮天空上≈隐形）
②`大小 W×H` 装不下字号（**实机会裁剪，编辑器预览有时不裁剪** → "预览有、实机没有"）
③内容为空。

## B. 脚本"没有日志"的真因顺序

排查顺序**必须是**：**先看画面里客户端控件出没出来 → 再看日志**。
控件没被创建出来（布局没被职业引用），挂在控件上的脚本**永远不会执行**，
日志一行都没有 —— 看起来像"日志功能坏了"，其实完全是两回事。

- 界面布局**必须被「职业」引用**：官方"玩家在关卡游玩时使用的界面布局，需要通过职业进行配置"。
  两条路：① `战斗预设 → 职业 → 选择布局`；② `界面控件组管理 → 界面布局 → 参数配置 →
  【打开玩家编辑】`（官方原话："界面布局的参数配置窗口也可以直接跳转到该编辑界面"）。
- 官方还明确：**"界面控件组库中制作的元件，实际游玩时并不显示，需要添加至界面布局中才会显示"** ——
  容器要走【界面布局】→【添加界面控件】，不是【界面控件组库】→【添加界面控件模板】。
- 布局改动要在【界面控件组管理】里点【**保存修改**】提交，再保存关卡，再试玩。

## C. ⚠️【自定义文本外显】被奇匠等级门控（文本只显示背景、不显示字）

官方教程原文（4 篇教程里都有这条注，其中一篇紧跟"教程中将以【文本框】进行讲解"）：

> **演示中的文本显示，需达到特定奇匠等级后解锁【自定义文本外显】功能，教程中以效果展示为主**

- **症状**：控件在、背景色在、**文字画不出来**（编辑器预览里能看到字，实机没有）。
  合理：背景走贴图/颜色通道，文字走**文本外显**通道，后者被等级门控。
- **在哪查**：ESC / 左上角菜单图标 → 系统菜单 → **「创作者(奇匠)等级」/「创作者(奇匠)权限」**
  （官方原文："创作者(奇匠)等级和创作者(奇匠)权限查看"）。
- **对本工程的影响**：UI 大量依赖文本（关卡名、计时、步数、线索文案、指认弹窗、结算）。
  - 优先方案：**把奇匠等级刷到解锁**，解锁后现有代码**一行都不用改**。
  - 备用方案：固定文案做成**图片素材**，用「图片控件」引用（适配层 `set_property(id,"image",…)` 已支持）；
    动态数字可用"数字图集"（0–9 十张图按位显隐）。
- **交叉验证（1 分钟）**：给 `cell.1.1` 预设按钮配**显示文本**。
  若图片能显示、文字不显示 → 与"文本外显未解锁"完全吻合。

## 一、坐标语义定案（此前一直是乱的）

标定方法：放几个**宽度不同**的白色占位图元在已知坐标上，截图后测包围盒反推。

结论 —— **两套坐标系，不要混**：

| 场合 | 语义 |
|---|---|
| **编辑器「位置 X, Y」输入框** | 控件**中心点**的**画布绝对坐标**；原点**左下**，Y 向上；**跟父级无关** |
| **脚本 `SetAnchoredPosition`** | 无父层级 → 画布左下为原点；**有父层级 → 与父级中心的相对偏移**（官方 API 文档 1317~1322） |
| **模拟器 `posX/posY`** | **与编辑器输入框完全一致**（实测：pos 就是中心点绝对坐标，父级被忽略，pivot/anchor 设置不生效） |

因为编辑器输入框和模拟器同语义，所以**一份 `layout-plan.json` 可以同时驱动模拟器预览和真机搭建指南**。
本工程因此在 `ui_controller.lua` 里引入了 **设计空间（1920×1080，左上原点、Y 向下）→ 画布空间（1600×900，左下原点、Y 向上，中心点绝对坐标）** 的单一换算点 `M.to_canvas()`。

## 二、三道门控（不打开 = 界面是死的）

### 门控 ② 容器必须打开「显示常驻光标」(`showCursor`)

模拟器里的派发条件（反编译原文）：

```js
cursorEventsEnabled(t) {
  for (let i = t; i; i = i.parent)
    if (i.kind === "container" && i.showCursor === true) return true;
  return false;
}
```

**症状**：界面完全正常，`OnInit` / `OnStart` 日志都打，但**点哪儿都没反应**，且没有任何报错。
**处置**：在最外层容器上勾「显示常驻光标」（`showCursor = true`）。

### 门控 ③ 脚本必须 `script:EnableUpdate(true)`

```js
runScriptPhase(t, i) {
  ... !(t === "OnUpdate" && !n.updateEnabled) && this.callGlobalDt(r, t, i)
}
// mountScript 里：updateEnabled: !1   ← 默认 false
```

**症状**极隐蔽：`OnInit`/`OnStart` 正常、日志正常，但 `OnUpdate` **一次都不执行** ——
计时器一动不动、单击的铅笔笔记永远落不了格（要等双击窗口）、等控件就绪的惰性重试也不发生。
**处置**：`entry_client_script.lua` 的 `enable_update()` 会调它，**不要删**。

### 门控 ④ 界面布局必须被「职业」引用

见上文附录 B。补充确证：模拟器里若把控件建在"服务端容器"之外，脚本按名字也找不到。

## 七、2026-09-26 真机首跑：**脚本终于执行了**（以及一个打崩 OnInit 的 `%d`）

### 7.1 结论先行

真机日志里出现了这些行 —— **它们全是脚本自己打出来的**：

```
[murdoku] 控件未找到：root / topbar / hud.title / … （一大串）
[murdoku] started: selftest_theft_5x5
[murdoku] destroyed
```

追了两天的「真机从没执行过」到此结束。走通靠三件事：
① `script:EnableUpdate(true)`；② 容器的「显示常驻光标」；③ 界面布局被「职业」引用。
（②本工程已改成脚本自己开，见 `Adapter:enable_cursor`。）

### 7.2 但同一份日志里有个**我自己写的 bug，把 OnInit 打崩了**

```
client_script:5991: bad argument #2 to 'format' (number has no integer representation)
	client_script:5991: in function 'check_canvas'
	client_script:6005: in function 'OnInit'
```

`check_canvas()` 里用 `%d` 去格式化 `game.GetUICanvasSize()` 的返回值，
而**真机返回的是浮点数** → Lua 5.3 直接抛错 → 因为没包 pcall，
**整个 OnInit 中断**：

- `adapter = Qianxing.new({...})` 没执行 → **配置全没生效**
- `Murdoku.prepare(adapter)` 没执行 → `OnStart` 拿着 nil 适配器继续跑，
  `Murdoku.start` 只好自己造了个**默认配置**的适配器
- 于是日志上表现为「找不到头像卡容器（cfg.tray_parent，默认 tray）」+ 一大串
  「控件未找到」—— 看着像"界面没搭好"，**其实是被一行日志打崩的**

**这个误导性极强**：如果没看出那条 `bad argument`，会一直以为是控件没建对。

### 7.3 修法（两条纪律，已落到代码里）

1. **打引擎给的数字一律 `%s` / `%.2f`，不用 `%d`。**
   Lua 5.3 的 `string.format("%d", 1600.0)` 会抛错，而 `%d` 是我们写日志时的手癖。
2. **OnInit 里任何诊断都不许有能力中断启动。**
   现在的顺序是：先 `pcall(build_adapter)`（把适配器建起来并交给 main），
   再各自 `pcall` 跑诊断（画布自检 / 信标）。诊断炸了最多少打一行日志。

另外补了：
- `Adapter:dump_names()` —— 探针失败时**把客户端控件树整个打出来**，
  「脚本说控件未找到，可你明明建了」这种问题一对照就知道差在哪（名字/层级/激活）。
- `build_adapter()` 抽成可重入函数，`OnStart` 发现适配器为空会**自己补建**。
- `tests/entry_smoke.lua` —— **离线**用假游戏环境把入口完整跑一遍
  （画布尺寸故意返回浮点 1600.0 和 1920.50），专防这类"把启动打崩"的 bug 复发。
  已并入 `tools/check_all.ps1` 的 5b 步。

> 这次事故的通用教训：**诊断代码的健壮性要求和主流程一样高**。
> 一行"只是打个日志"的代码，只要它在初始化路径上又没有保护，
> 就有能力让整个功能看起来"完全没生效"，而且报错信息和真实原因隔了十万八千里。

### 7.4 还没确认的：真机画布到底多大

## 7. 文件编码：两条**相反**的规则，都会踩

2026-09-26 又踩了一次，而且这次是"修好了又被工具改回去"，所以单独记一节。

| 文件类型 | BOM 状态 | 不遵守的后果 |
|---|---|---|
| `.ps1`（含中文） | **必须有** UTF-8 BOM | Windows PowerShell 5.1 把无 BOM 文件按 **GBK** 读 → 中文变乱码 → 解析器在**看起来完全正常的那一行**报 `The string is missing the terminator` / `The hash literal was incomplete`。真实报错位置还要往前找。 |

### 7.1 为什么反复复发

`edit` 工具**每次写入都会剥掉 BOM**。所以：
改 `check_all.ps1`（哪怕只加一行）→ 保存 → 下次运行直接解析失败。

本轮就是这样：改完明明跑过一次自检，加了两步之后整份脚本又炸了。

### 7.2 永久对策

`tools/normalize_encoding.ps1`（**纯 ASCII，自身不需要 BOM**）：

```powershell
powershell -ExecutionPolicy Bypass -File tools\normalize_encoding.ps1          # 修
powershell -ExecutionPolicy Bypass -File tools\normalize_encoding.ps1 -Check   # 只报告，错了 exit 1
```

并且已经挂进 `tools/check_all.ps1` 的 **2c/13** 步（`-Check` 模式）——
以后任何一次"改完 .ps1 忘了补 BOM"，自检会直接指出来，而不是等脚本解析炸掉。

**规矩**：手改任何 `.ps1` 之后，先跑一次 `normalize_encoding.ps1`，再跑 `check_all.ps1`。

## 8. PowerShell 的 `-eq` 会按**左操作数**类型强制转换（假绿陷阱）

2026-09-26 在做 `check_all.ps1` 的"三态汇总"（通过 / 失败 / 跳过）时踩的：

```powershell
$r.OK -eq 'SKIP'      # ← $r.OK 是 [bool] $true 时，这个表达式是 $true ！
```

原因：PowerShell 的 `-eq` **不是**严格相等，它会先把右操作数转成**左操作数的类型**再比。
于是 `'SKIP'` 被转成 `[bool]` → `$true`，字符串比较根本没发生。

**后果**：17 步全部显示成 `SKIP`，而实际上 1~7 步是真跑过的（`exit=0`）。
如果反过来写（把 `SKIP` 当"通过"），就会得到"跳过也算通过"的**假绿**——
这正是 `check_all.ps1` 一直在防的东西，结果被一个运算符语义绕过去了。

**正确写法**：把字符串常量放在**左边**。

```powershell
if ($r.OK -eq $false) { ... }            # 左操作数是 [bool]，正常
elseif ('SKIP' -eq $r.OK) { ... }        # 左操作数是 [string]：'True' -ne 'SKIP' ✔
```

> 同类坑：`$null -eq $x` 也是社区推荐的写法（`$x -eq $null` 在 $x 是数组时会做过滤而不是判空）。
> 一句话记住：**判断"是不是某个字符串/枚举"时，把常量放左边。**

## 9. 真机 12:20 日志暴露的两个「时机」bug（都是我的）

第一份成功的真机日志（2026-09-26 12:20）里，除了预期内的「控件还没搭」，
还暴露了**两个我自己的 bug**，都属于"阶段性问题"—— OnInit 阶段控件树是空的，
而我有两处代码没考虑这件事。

### 9.1 PC 键盘从真机第一次运行起就没绑上过

日志：

```
[murdoku] 键盘绑定跳过：找不到可接收按键的控件（root）。不影响鼠标/触摸操作。
[murdoku] 键盘快捷键没绑上（不影响鼠标/触摸操作）
```

**根因**：`bind_keys` 只在 `OnInit` 里调一次，而 **`OnInit` 阶段控件树是空的**
（同一次日志里 `共 0 个节点`、约 0.5 秒后才有节点）。所以：

- `find("root")` 返回 nil → 一个键都没绑上；
- 从此**再也没有补绑的时机** → 真机上 PC 键盘快捷键（方向键移动光标 /
  空格笔记 / 回车放置 / 1..7 选人 / Tab 换工具）**一直都是死的**。

**为什么容易被放过**：那句日志的措辞是"不影响鼠标/触摸操作"，听起来无关紧要，
而它确实是**可选功能** —— 但"可选"不等于"可以永远不生效"。

**修法**：把绑定做成**可补绑**（`bind_keyboard_once`）。OnInit 试一次；
控件树就绪后（OnStart 探针通过 / OnUpdate 重试成功）再补一次，成功就记下来不重复。

> 教训：**任何"只在一个生命周期钩子里做一次"的控件相关操作，都要怀疑一下**
> 那些钩子的执行时机。OnInit 时控件树为空是实测事实。

### 9.2 OnInit 把"树是空的"报成了故障

日志：

```
[murdoku] 找不到 board / cell.1.1，下面把「脚本能看到的客户端控件」全列出来
[murdoku] ===== 客户端控件树（脚本能看到的，共 0 个节点）=====
[murdoku] 客户端控件树是**空的**（0 个节点）。控件没被创建出来，最可能是下面三条之一：
[murdoku]   ① 界面布局没被【职业】引用 …
```

**根因**：探针 `probe_or_dump()` 在 OnInit/OnStart 也跑，而那时候树**本来就是空的**。
于是它把"三条病因"全砸出来了 —— 看着像出了大故障，其实一切正常
（同一次日志后面就找到了 board 和 cell.1.1，正好自证）。

**修法**：探针先**只数不打印**（新增 `Adapter:count_names`，`dump_names(..., quiet)`），
再分轻重：

| 情况 | 话术 |
|---|---|
| 树是空的、**还有重试机会** | 一句"控件树还没就绪（属正常）→ 稍后重试"，不打树、不打病因 |
| 树是空的、**已放弃重试** | 完整 dump + 三条病因（这时候才是真故障） |
| 树里**有节点**但缺 board/cell.1.1 | 立刻 dump + 名字近似提示（等下去也没用） |

回归防线：`tests/entry_smoke.lua` 第 3 节现在**反向**断言 ——
OnStart 阶段**不许**出现「客户端控件树」和「三条病因」；第 4 节断言放弃时**必须**出现。

### 9.3 顺带修的：`控件未找到` 刷了 80+ 行

真机首次开局会缺 80 多个控件（界面还没搭完），原来一个控件一行，
把"缺的是哪几类"这个真正有用的信息彻底淹掉了。

改成**收集 + 分组汇总**（`Adapter:_note_missing` / `report_missing`），
在第一次渲染后打一次：

```
[murdoku] 这些控件还没建（共 86 个，按类分组）：
[murdoku]   cell.*    ×24   cell.1.2 cell.1.3 cell.1.4 …
[murdoku]   intro.*   ×6    intro.dots intro.title intro.body …
[murdoku] 完整 150 个控件的名字/坐标/父子关系：docs/控件坐标表-1600x900.md
```

### 9.4 一致性教训：**报告不要走 stderr**

新加的「格子体检」一开始把整段报告打在 `printerr` 上。结果
**模拟器回归的两步立刻挂了** —— 因为 `play_test.mjs` / `win_path.mjs` 会把
"运行期有没有错误日志"当健康判据，于是一份全是 ✅ 的体检报告被算成错误。

**规矩**：`print` = 信息/报告，`printerr` = 真的出问题了。
模拟器把这个区分当断言用，所以别拿 `printerr` 打"报告"。

## 10. 模拟器回归是**时序敏感**的：别在它跑的时候并行干活

2026-09-26 遇到一次「幽灵回归」：

| 现象 | 单独跑 | 在 `check_all.ps1` 里跑 |
|---|---|---|
| `win_path.mjs --level=case_002` | ✅ 6/6 放置 | ❌ 5/6 |
| `probe_cursor.mjs` | ✅ 4/4 | ❌ 3/4（双击放置 0/5） |

**排查过程**：两个用例单独跑都稳定通过、重跑两次也通过；
干净地重跑整个 `check_all.ps1`（这次我**不做任何并行操作**）→ **18/18 全绿**。

**结论**：那两次失败是我自己造成的 —— 我在 `check_all` 跑的同时还在并行执行
grep、写文档、开 PowerShell。模拟器里的**双击判定窗口（0.35s）**和逐步推进
对时序敏感，机器一忙就会抖。

**规矩**：

- 跑 `check_all.ps1`（尤其 8~13 那几步模拟器用例）时**不要并行做重活**；
- 看到模拟器用例失败，先**单独重跑那一个**：
  `node tools\sim\win_path.mjs --level=case_002` / `node tools\sim\probe_cursor.mjs`；
  单跑通过 → 是抖动，不是回归；
- 真正由代码引起的失败是**可复现的**：`entry_smoke` / `probe_input` 那两次
  每一步都稳定挂，改完代码立刻就好 —— 那才是回归。

## 11. 素材「图片类型」的真实限制：**只有底板 / 分稿线能拉伸**

> **用户真机发现（2026-09-26）**：在「图片源 = 静态引用」里选素材时，
> **只有「底板」和「分稿线」两类支持【图片类型 = 拉伸】**；
> 其余图形（**包括 `x` 要用的「功能图标」**）**只有【基础】**一种。

这条**推翻了我之前的一个假设**：我原来在 `assets/placeholder/README.md` 里直接写
"图片类型选拉伸"，默认所有素材都能选拉伸。**不成立。**

### 11.1 官方文档其实写了，只是很容易读漏

《图片控件》（`mh2oih9jou22`）原文：

> 图片类型：支持配置基础、拉伸。**部分图片资产具有拉伸属性**，
> 可以通过图片资产库中的筛选项进行查找

"**部分**"两个字就是这件事 —— 不是所有素材都有拉伸属性。
我上次修订那个文档时把这段抄进去了，但**没有把它当约束去核对每个控件**，是我的疏漏。

### 11.2 影响面：哪些控件必须换方案

| 控件 | 需要随控件缩放 | 能拿到拉伸 | 结论 |
|---|---|---|---|
| `cell.<r>.<c>.face` 格面底图 | ✅ | ✅ 底板可以 | **用底板类素材** |
| `cell.<r>.<c>.x` 的 X 图标 | ✅ | ❌ 功能图标只有基础 | **改成"原始尺寸就塞得下"的小图** |
| `cell.<r>.<c>.note` 铅笔笔记 | ✅ | —（文本框，不走图片） | 不受影响 |
| `tray.<id>.face` 头像卡底 | ✅ | ✅ 底板可以 | 用底板类 |
| `tray.<id>.face` 换上的**角色头像** | ✅ | ❌ 头像属图标 | ⚠️ **待验**，见 11.4 |
| `btn` / `panel` 底图 | ✅ | ✅ 底板可以 | 用底板类 |

**为什么这个限制很要命**：格子边长是**自适应**的（5×5 / 6×6 / 7×7 → **135 / 113 / 97 px**），
而不能拉伸的图标如果**原始尺寸大于 97px**，就会**盖住旁边的格子**。

### 11.3 已做的调整（占位素材）

`tools/make_placeholder_assets.ps1` 现在把两类**分开处理**：

| 类别 | 文件 | 尺寸策略 |
|---|---|---|
| **底板类**（可拉伸） | `cell_face/hover/pressed/disabled`、`btn_*`、`card_face`、`panel_*`、`bg_screen` | 照旧写大，靠拉伸填满控件 |
| **图标类**（只有基础） | `x_mark.png` **256 → 88**、`portrait_*.png` **128 → 64** | 按"**原始尺寸也不溢出**"定：88 < 最小格子 97；64 < 头像卡宽度（7 人关 68） |

### 11.4 还剩两件要真机验的事

**① 「基础」到底是原始尺寸，还是也会按控件缩放？**

官方只说了"支持配置基础、拉伸"，没说「基础」的渲染语义。两种可能：

- **基础 = 按原始像素画**（我按这个假设做的防护，即上面的小图尺寸）；
- **基础 = 按控件尺寸缩放，只是四角会跟着形变**（那 88px 的图会被拉满格子，也没问题）。

**验证方法**：把 `x_mark.png` 挂到 `cell.1.1.x` 上，试玩时点 X 工具划一格，看：
- X **刚好在格子中央、不超出** → 基础 = 原始尺寸（小图策略正确）；
- X **铺满整个格子** → 基础 也会缩放（那尺寸就无所谓了，可以换回大图）。

**② `face` 是底板+拉伸，但脚本会 `SetImage` 把它换成图标类的头像 —— 会怎样？**

`tray.<id>.face` / 破案时的格面都要换头像，而头像属图标类。两种可能：

1. 控件**保持拉伸** → 头像被拉满（我们想要的效果）；
2. 引擎按新素材的属性**退回基础** → 头像按原始 64px 画在中间（也能看，只是小）。

**验证方法**：点头像卡选中角色 → 双击落子，看格子里的头像是**铺满**还是**小小一张**。

> **两种结果都不影响玩法** —— 玩家是靠头像卡上的**名字文字**认人的
> （`assets/placeholder/README.md` 里已经写明这一点）。

### 11.5 教训

**"官方文档里有这句话" 和 "我按这句话核对了每个控件" 是两件事。**
这条限制本来就在我抄进文档的原文里，但我没有把它变成一张**逐控件的核对表**，
所以就漏掉了 —— 直到你在编辑器里一处一处试出来。

以后遇到"某属性只在部分情况下可用"的官方措辞，要立刻落成
「哪些控件 → 能不能用 → 不能用时的替代方案」三列表。

## 12. 【更正 §11】「基础 / 拉伸」的真正区别 —— 我上一节的推论错了一半

> **用户在真机上做了实验（2026-09-26）**：
> **基础格式和拉伸格式都会随图片控件本身的大小变化（总是填满图片控件本身）。**
> 所以"不能用拉伸的图会按原始尺寸画、会溢出控件"这个推论**是错的**。

### 12.1 我错在哪

我在 §11 里从官方那句话推出：「只有底板/分稿线能拉伸 → 功能图标只能基础 →
基础 = 按原始像素画 → 大图会盖住邻格」。**第一步到第二步是对的，第三步是我编的** ——
官方从没说过「基础」是按原始尺寸画。用户一实验就把它推翻了。

我当时还基于这个错推论**把 `x_mark` 从 256 缩到 88、头像从 128 缩到 64**（做"防护"）。
那两个尺寸留着无害（纯色图怎么缩放都一样），但**理由是错的**。

### 12.2 官方原文的真实结构（抓原始 HTML 确认）

之前我把那张表读成了「图片类型」的选项。抓 [图片控件原文](https://act-webstatic.mihoyo.com/ugc-tutorial/knowledge/cn/zh-cn/mh2oih9jou22/content.html?v=1016)
看 HTML 结构，实际是**两个不同的概念**：

```
_图片类型：_支持配置基础、拉伸。部分图片资产具有拉伸属性，可以通过图片资产库中的筛选项进行查找
   ↓（紧跟一张表，表头是「图片属性」，不是「图片类型」）
| 图片属性 | 特性 | 常见用途 |
| 普通     | 图片拉伸时四角会跟随形变 | 拼接特定形状或基础图案 |
| 三宫格   | 横向或纵向其中一个方向拉伸时，四角维持原有形状 | 按钮、页签项的底板 |
| 九宫格   | 横向或纵向拉伸时四角都保持原有形状 | 列表项底板、页签、背景 |
```

| 概念 | 归属 | 取值 |
|---|---|---|
| **图片类型** | **控件**上的设置（`Enum.ImageType`，脚本**读写**） | 基础 / 拉伸 |
| **图片属性** | **素材自己**的属性（在图片资产库里筛） | 普通 / 三宫格 / 九宫格 |

### 12.3 于是区别是这样（与实验完全吻合）

「拉伸」不是一个独立的缩放算法 —— 它是"**启用该素材的拉伸属性**"。
而素材的拉伸属性由「图片属性」决定：

| 素材的图片属性 | 拉伸时四角 | **基础 vs 拉伸 有区别吗** |
|---|---|---|
| **普通** | 跟随形变（角也被压） | ❌ **看起来完全一样** —— 两者都铺满控件、角都形变 |
| **三宫格** | 单向拉伸时那一对边不变 | ✅ 有：拉伸 保住边，基础 压扁 |
| **九宫格** | 双向拉伸时四角都不变 | ✅ 有：拉伸 保住圆角，基础 把圆角压扁 |

**用户实验里试的是「普通」属性的素材**（功能图标之类），所以怎么看都一样 ——
**实验结论正确，而"没有区别"只对普通素材成立。**

### 12.4 更正后的实际影响（比 §11 说的小得多）

| 问题 | §11 的错误结论 | **实际** |
|---|---|---|
| 图标（x / 头像）能不能铺满控件 | ❌ 不能，会按原始尺寸溢出 | ✅ **能**，基础也铺满 |
| 拉不拉伸会不会让棋盘花掉 | ❌ 会 | ✅ **不会** |
| 素材是不是必须做成小图 | ❌ 是 | ✅ **不用**，尺寸随便 |
| 拉伸属性到底影响什么 | （说错了） | 只影响**有圆角/边框的美术会不会被压扁** |

**所以 §11 里"这条限制很要命"的定性要撤回 —— 它不阻塞任何事。**

### 12.5 更正后真正该守的规矩

| 场景 | 怎么做 |
|---|---|
| 纯色 / 纯图案素材（占位图、色块） | 基础 / 拉伸 **随便选**，都一样 |
| **有圆角 / 边框的美术**（按钮、面板、卡片底图） | 素材做成 **九宫格**（或三宫格），图片类型选 **拉伸** → 圆角不被压扁 |
| 格面底图 | 纯色无所谓；**带描边的方框素材**建议做九宫格 + 拉伸 |
| 尺寸怎么定 | **不看尺寸，看长宽比** —— 因为总是铺满控件，长宽比不对才会被拉变形 |

> **最后一条最重要**：既然总是铺满，那就**必须让素材长宽比 ≈ 控件长宽比**，
> 否则会被拉变形。例如头像卡是 68×87（接近 3:4），头像素材就该是 3:4 而不是正方形。

### 12.6 又一次教训

**不要用"从官方措辞推出来的机制"去替代"在真机上做一次实验"。**
§11 里我把两个概念（图片类型 / 图片属性）读混了，然后顺着错的理解往下推了两层，
还据此改了素材尺寸、写了"很要命"的结论。你花两分钟做了个实验就推翻了。

以后遇到这种"属性到底怎么表现"的问题，**先写成一句可实验的假设，让你在编辑器里试**，
而不是直接写进文档当结论。文档里凡是**推测**出来的机制，都要显式标注"未验证"。

## 13. 「另存为模板」**不是** `InstantiateClientUIControl` 要的那种模板（真机 14:45 日志）

### 13.1 键盘：我用的根本不是键码，而是**语义事件**

官方签名是：

```
AddKeyEventListener(eventType, callback)
```

第一个参数是 **`Enum.KeyEventType`**（「设备 + 语义 + 按下/抬起」，共 **164** 项），
而不是键码。我一直传 `Enum.KeyboardKeyCode.X` / `Enum.KeyCode.X` / 裸字符串 ——
三者都不是合法 eventType，于是 **30 个调用全部抛错**（所以日志是"成功 0 个，失败 30 个"）。

真实的名字长这样（括号内是该事件的**默认物理键**）：

| `Enum.KeyEventType` | 含义 | 默认键 |
|---|---|---|
| `KeyboardCraftspersonKey1..43Down` | 键鼠：奇匠按键1..43（按下） | `1..9`,`0`,`U Z Y G H I O P J K L V`,`F5..F10`,`` ` ``,`-`,`=`,`[`,`,`,`.`,`/`,**`↑ ↓ ← →`**,右Ctrl,右Shift,Backspace,CapsLock |
| `KeyboardMoveForward/Backward/Left/RightKeyDown` | 前后左右移动 | `W S A D` |
| `KeyboardJumpKeyDown` | 跳跃 | `Space` |
| `KeyboardDropKeyDown` | 落下 | `X` |
| `KeyboardOpenShortcutWheelKeyDown` | 呼出快捷轮盘 | `Tab` |
| `KeyboardInteractKeyDown` | 拾取/交互 | `F` |
| `KeyboardNormalAttackKeyDown` | 普通攻击 | **鼠标左键** |
| `KeyboardCharacterSkill1..4KeyDown` | 角色技能1..4 | `E Q R T` |

**三个要点**：

1. **`Enum.KeyboardKeyCode` 是另一个东西** —— 它只给「按键提示控件」
   （`ClientUIKeyHintControl.keyboardKeyCode`）**显示**用，不是事件。
2. **没有 `Return` / `Enter` / `Escape` 事件** → 放置改绑「拾取/交互」(F)、
   "关弹窗/选关"改绑奇匠按键42 (Backspace)。
3. **「奇匠按键」是可被玩家重映射的槽位**，上面那些物理键只是**默认值** ——
   所以界面文案要写语义说法，不能假定玩家按的一定是 ↑↓←→。

**修完之后模拟器实测**：`键盘快捷键已绑定 24 个键　[绑在 root 上，成功 24 个]`，
数字选人 + 方向键移光标 + F 放置全部生效。

### 13.2 格子模板：「另存为模板」存出来的索引**客户端脚本调不动**

`InstantiateClientUIControl` 的官方说明是「根据**已配置的控件模板索引**，在 parent 下创建控件实例」。
而《客户端控件和客户端脚本的定义》里有一条**硬约束**：

> 除**客户端控件容器画布中的客户端控件**以及**客户端控件模板中的控件**外，其他控件均为**服务器控件**，
> **服务器控件的模板索引无法被客户端脚本调用**。

所以：

| 索引来源 | 能不能实例化 |
|---|---|
| `cell.1.1` 的 `1073741848`（内置「预设按钮」基础模板） | ❌ 返回 nil |
| 右键【另存为模板】得到的 `1073741864` | ❌ 也返回 nil（不在"客户端控件模板"体系里） |
| **界面控件组库 →「客户端控件模板」里存出来的** | ✅ **这才是"已配置的控件模板"** |

**正确入口**（官方原文）：

> 界面控件组管理 → **界面控件组库** → **客户端控件模板** → 点击【**添加客户端控件**】
> → 选择添加所需的客户端控件 → **存为模板**

而且官方还写了：「编辑时，可以通过**点击客户端控件查看对应的控件模板索引 ID**」——
所以拿得到那个 ID，可以**直接把数字填进 `cfg.cells.prefab`**（比放 `tpl.cell` 更稳）。

### 13.3 我这一轮走弯路的教训

我上一轮让你"右键 `cell.1.1` →【另存为模板】→ 从模板新建控件"，**是从 `ensure_cells` 报错信息
里的旧提示抄下来的**，而那句提示本身就没核对过官方文档。

## 15. `focus_clue` 死按钮 —— 发出但没处理分支（2026-09-27 修复）

**怎么发现的**：新写的对账工具 `tools/audit/check_actions.mjs`
把「界面发出的 `action`」和「分发器 `a == "..."` 的分支」对了一遍：

```
发出的 action 26 个
分发器处理的分支 25 个
[!] 发出但【没有处理分支】的 1 个：focus_clue   发出处 ui_controller.lua:827
```

**根因**：线索卡在 push 时就带了 `event = { action = "focus_clue", index = i }`，
但分发器（`ui_controller` 的 555~692 行那一串 `elseif a == ...`）**从来没有这个分支** ——
所以点线索卡**完全没反应**，而且离线/在线都只是"安静地什么都不做"。

**修法**（两处，都用已有机制，不引入新资产）：
1. `ui_controller.lua` 分发器补 `elseif a == "focus_clue"`：
   切换 `self.focused_clue`（再点取消），并用**已有的** `M.EFFECTS.CLUE_IN` 特效做可见反馈。
2. 线索卡 push 的 `style` 加上 `clue.focus`；`engine_adapter` 的 `key == "style"` 分支
   补一行 `elseif value == "clue.focus" then scale = 1.03`。

**为什么反馈走特效而不是样式**：adapter 的 `style` 分支**只对少数已知样式**做缩放，
未知样式是**静默忽略**的（`engine_adapter_qianxing.lua` 的 `key == "style"`）——
只加样式不加分支，等于什么都没发生。

**固化**：`check_actions.mjs` 已接进 `tools/check_all.ps1` 作为 **2i/13** 步骤，以后回归会被抓到。

### 另一个教训：不要在脚本运行时改它

`check_all.ps1` 后台跑到一半时，我并发跑了 `normalize_encoding.ps1`（它会重写文件补 BOM），
结果 PowerShell **边读边执行**，读到了半截文件 → 一堆 `ParserError` + 中文乱码
（`鐢熸垚鐪熸満...` = UTF-8 被按 GBK 读）。**看起来像代码炸了，实际是并发改文件。**
⇒ 改文件的操作绝不与"正在执行的脚本"并发。

## 16. 结构错位：HUD 混入按钮、ruler 被埋在 board 下（2026-09-27 修复）

**用户反馈**：① 只有七个容器 ② 缺少 ruler 部分 ③ HUD 中混入了 action 和 tool。

**先查是不是我生成错了** —— 不是。用 `tools/gil/plan_tree.mjs --diff 完整界面2.gil` 对账：

```
父级一致 101，不一致 0，缺失 0
```

规划（= `ui_controller.lua`）本身就是那么定义的：

| 现象 | 规划里的实情 |
|---|---|
| `root` 下只有 7 个节点 | `tray`/`clues` 嵌在 `left` 下（5 容器 + 2 面板 = 7） |
| 找不到 ruler | `ruler.c.*`/`ruler.r.*` 的父是 **`board`**，和 49 个格子挤在一起（board 子树 63 个子控件） |
| HUD 混着 tool/action | `tool.*`/`action.*` 的父也是 **`topbar`**，和 4 条 HUD 文字同层（topbar 12 个子控件） |

### 修法：加两个分组容器，**只改 parent、不动 rect**

```lua
-- ui_controller.lua
push({ id = "toolbar", ... parent = "root",  rect = rect_of(L.topbar) })   -- 工具/操作按钮归它
push({ id = "ruler",   ... parent = "board", rect = rect_of(L.board) })    -- 坐标尺归它
```

**为什么敢只改父级**：`ui_controller` L56 写着 `rect` 是**设计空间绝对坐标**
（`cx = round((r.x + r.w/2) * s)`），所以换个父级不会移动任何控件。

**证明**：`tools/gil/plan_diff.mjs 旧计划 新计划` → `几何被移动的控件：0 ✅`。

修完：`root` 下 8 个容器/面板、`topbar` 只剩 4 条 HUD、`toolbar` 8 个按钮、
`ruler` 14 个刻度、`board` 从 63 个子控件降到 2 个。

### ⚠️ 途中被自己的工具抓到的一个 bug

改完父级后 `plan_diff` 立刻报 12 个 ruler 刻度**几何变了**（尺寸 97 → 135）。
根因在 `tools/dump_layout.lua` 的并集逻辑：

```lua
local adaptive = (n.parent == "board" or n.parent == "tray")   -- 只看直接父级
```

「自适应控件」（格子/头像卡/坐标尺 —— 尺寸随关卡 N 变）**只看直接父级**。
