# 2D 界面 与 3D 角色：**怎么让键盘/点击不落到角色身上**

> 来源：官方《客户端 Lua UI 脚本公共 API》
> （本地缓存：`docs/api-cache/mhtakr07vej4.txt`，抓自
> https://act.mihoyo.com/ys/ugc/tutorial/detail/mhtakr07vej4 ）
>
> 提出这个问题的背景：我们的界面用 `AddKeyEventListener` 收键盘，
> **而 3D 角色也会同时响应同一批按键** —— 玩家在选关界面按方向键，
> 角色会在背后跑起来。

---

## 一、结论：**不是"拦截键位"，是给容器开"屏蔽穿透"**

官方 API 文档第 24 节 **`ClientUIContainerControl`（容器节点控件）** 里，
有四个**读写**字段：

| 字段 | 类型 | 访问 | 说明 |
|---|---|---|---|
| `disableKeyEventPassthrough` | boolean | **读写** | **是否屏蔽按键事件穿透** |
| `disableCursorEventPassthrough` | boolean | **读写** | **是否屏蔽区域内点击事件穿透** |
| `isolateNavigation` | boolean | **读写** | 是否隔离手柄导航 |
| `showCursor` | boolean | **读写** | 是否显示常驻光标 |

原文（文档 1883~1898 行）：

```
isolateNavigation              boolean  读写  是否隔离手柄导航
disableKeyEventPassthrough     boolean  读写  是否屏蔽按键事件穿透
disableCursorEventPassthrough  boolean  读写  是否屏蔽区域内点击事件穿透
showCursor                     boolean  读写  是否显示常驻光标；
                                              CursorEvent相关方法都需设置该参数为真后才可正常使用
```

**⇒ 把一个容器（连同它下面所有子控件）设成"屏蔽穿透"，
这一块区域的按键/点击就会被界面吃掉，不再传给 3D 角色。**

**不需要**自己去 `AddKeyEventListener` 里拦截、也不需要维护"按键黑名单"。

---

## 二、为什么是这个方案

(见下：这个字段本项目早就在用了)

## 二·补：**这个字段本项目早就在用了 —— 只是方向相反**

查完文档我回头一看，适配器里**本来就有这两个字段**
（`engine_adapter_qianxing.lua` 的 `open_click_passthrough`）：

```lua
-- 为了让**棋子能点得动**，当时把"屏蔽穿透"关掉：
mid.disableCursorEventPassthrough = false
mid.disableKeyEventPassthrough    = false
```

**⇒ 机制一直在手上，我只是从没把它和"挡住 3D 角色"联系起来。**

所以对主页要做的事，本质上就是**反向使用同一个开关**：
- **棋盘/棋子**所在容器：`false`（要让点击落到棋子上）
- **主页/选关等纯 UI 面板**：`true`（不要让按键落到角色身上）

> 这条也说明：**排查"某功能有没有现成支持"时，
> 先搜自己的代码里有没有用过那个字段** —— 比重新设计一套更省事。



| 方案 | 可行性 | 说明 |
|---|---|---|
| **容器 `disableKeyEventPassthrough`** | ✅ **官方支持** | 一个字段搞定，覆盖整棵子树 |
| 自己拦截键位 | ❌ 不可靠 | `AddKeyEventListener` 只是**监听**，没有"消费掉"的语义 —— 监听无法阻止引擎把按键交给角色 |
| 维护按键黑名单 | ❌ 脆弱 | 要枚举所有会被角色响应的键（含奇匠按键重映射），必然漏 |

> ⚠️ 这也解释了为什么"拦截"思路走不通：
> **监听 ≠ 消费**。文档里没有提供"吞掉按键"的 API，
> 官方给的解法是在**容器**层面屏蔽穿透。

---

## 三、怎么用

### 编辑器里
选中容器 → 属性面板 → 勾「屏蔽按键事件穿透」/「屏蔽区域内点击事件穿透」。

### 脚本里（本项目习惯）
`ClientUIContainerControl` 的字段是**读写**的，所以脚本能设。
本项目的适配器**已经在给容器设 `showCursor`**（日志里的
「已由脚本打开 10 个容器的「显示常驻光标」」），
加这两个字段是同一类操作：

```lua
-- 概念示意（实际走 adapter:set_property 的容器分支）
ctrl.disableKeyEventPassthrough = true      -- 按键不穿透给角色
ctrl.disableCursorEventPassthrough = true   -- 点击不穿透
ctrl.isolateNavigation = true               -- 手柄导航隔离
```

### ⚠️ 放置位置很重要
- 要屏蔽的是**整块界面区域**，所以应该设在**根容器 / 各面板容器**上，
  而不是设在某个按钮上。
- 本项目现在的容器：`root` / `topbar` / `toolbar` / `left` / `right` / `tray` /
  `board` / `ruler` / `intro` / `modal`（共 10 个，正是日志里那 10 个）。

## 四、对"主页选关"的意义（待做）

主页/选关界面是**纯 2D 操作**，而且很可能**没有棋盘**，所以：

1. **主页容器设 `disableKeyEventPassthrough = true`**
   → 玩家在选关时按方向键，3D 角色不会乱跑。
2. **进入关卡后**再决定要不要恢复穿透 ——
   本作是纯鼠标点选玩法，**大概全程都该屏蔽**，
   但这点要等实际试玩再定（例如"想留一个键给角色跳一下"之类的需求）。
3. **手柄**：`isolateNavigation` 同理（社区资料少，**列为待实验项**）。

## 六、★ 那个"会不会误伤自己"的风险 —— **已经界定住了**

唯一让人不放心的地方：**屏蔽按键穿透之后，脚本自己的键盘快捷键还收得到吗？**

### 结论：**最坏情况也没有实际损失**

三条事实叠起来：

1. **键盘监听绑在 `root` 上**
   （`entry_client_script.lua` 的 `bind_keyboard_once` → `adapter:bind_keys` →
   `cfg.key_control`；真机日志：「**绑在 root 上，成功 24 个**」）
2. **我们屏蔽的是 `home` 和 `select`** —— 它们是 `root` 的**子**容器
   （`main.lua`：`seal_containers({ "home", "select" })`）
3. **子容器上的"屏蔽穿透"不会撤掉挂在父容器（`root`）上的监听器** ——
   两者是不同机制：`AddKeyEventListener` 是**控件自己的回调**，
   `disableKeyEventPassthrough` 管的是**按键要不要继续传给 3D 世界**。

**⇒ 最坏情况**：在主页/选关界面上，脚本收不到键盘 ✅
**⇒ 而这两个界面本来就是纯鼠标点的**（没有棋盘、没有格子、没有键盘光标）✅
**⇒ 关卡内的键盘快捷键完全不受影响**（那些容器我们没屏蔽）✅

### 换句话说

**这个设计即使猜错了，也只会"在不需要键盘的界面上屏蔽键盘"** —— 可以接受。

反过来，**如果哪天要给主页加键盘操作**（比如方向键选卡片），
把 `main.lua` 里那行 `seal_containers` 去掉即可 —— 一行的事。
