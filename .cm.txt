fix: stop discarding a row's letter, which is what turned DEF into AAF.

The device log named it precisely. Two adjacent lines for row.3.4:

    letter for the same person configured twice: who=4 already recorded=A, this row=D
                                                -> keeping the first one
    source recorded: row.3.4 -> who=4 letter=D

The row read D correctly and then threw it away, so rows 4 and 5 kept A while row 6 kept F --
the AAF the user reported, exactly.

The cause is mine. That first-come-first-served guard was written in the previous round for the
who-text key, where two rows legitimately carry the same who and one had to win. The user has
since fixed the key as the row number, so the premise no longer holds: a row has exactly one
author, and the guard has nothing to arbitrate. Worse, it compared across namespaces. The key
was tonumber(_pid) on a row number, so it read _row_letter[4] -- a slot that a previous level
may have written, or that the older who-keyed version left behind -- and treated two unrelated
things as a conflict. It looked like protection and was destruction.

The write is now unconditional on the row key, which is correct by construction: a row has one
letter, and the last read of that slot is its truth. The guard is replaced by one that can
actually fire, a single row configured with two different letters, which cannot be a false
positive from another level or the other namespace.

level3_letter_map gains section 2b, which is the part I had been missing. Every earlier assertion
ran on an empty table, where overwriting and not overwriting are indistinguishable -- so the
whole suite was blind to this by construction. 2b seeds the table with wrong values first, which
is the state the device is in when it reaches level 3, and asserts each row takes its own letter.
I verified it catches the bug by restoring the old guard: three assertions go red and the file is
restored byte-for-byte. That is now tools/verify_row_overwrite_sentinel.mjs.

The row/piece/letter dump added last round is what made this findable, and it has earned its
place: it showed the rows were configured D, E, F while the board said A, A, F.
