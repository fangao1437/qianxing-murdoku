### 6.3 构建器执行流程（`构建657_关卡内UI.mjs`）

1. `readGil(INPUT)`；**先校验 SHA256**，不符直接抛错；`OUTPUT` 已存在且无 `FORCE=1` 直接抛错。
2. 载入 `gilread.mjs` / `gilwrite.mjs` / `ops.js`；按规格顺序执行 `existingOps`（`setNum` 写颜色、`setGeom` 写四个状态块、`setHiddenRecord`）。
3. 新增层：`cloneField(原型)` → 递增 `g.maxId` → `remap` 旧 id → `textsOf` 覆写实例名 → 去掉旧 `#504` 父引用并写入新 `parent.id` → 清空克隆来的 childList → 追加到 `g.tree` 的 `#9` 记录表 → `ensureChildListTop(parent)` + `setChildList` 追加 → `setGeom` → `setHiddenRecord(f,false)`。
   - 图片层原型 `td.home.page.1.help619.icon`；文本层原型 `td.l1.page.1.heading`（与 641 一致）。
   - ID 只从 `g.maxId` 递增，**不复用任何已隐藏/已删除记录的 id**。
4. `writeGil()` 是**唯一落盘通道**（禁止自己 `fs.writeFileSync` 一个 `.gil`），它自带 6 道闸：编码 → 输出必须不同于输入 → 落盘 → **从磁盘重新读** → 往返编码逐字节一致 → 字段级 diff 条数断言。
5. 断言：内嵌 Lua 叶子与输入逐字节相同（636,341 B）；`police-v12` 组及 761 子控件 0 改动；`stage`/`board.floors`/`board.rugs`/`cell.*` 0 改动；`clue`/`row`/`letter` 文本字段 0 改动；无悬空 parent；新增记录数与预期一致。
6. 输出审计 JSON（体例对齐 `656_构建审计.json`）。

> **本目录的构建器默认是 DRY-RUN**：只打印操作清单与预计记录数，不调用 `writeGil`、不产生任何 `.gil`。
> 只有显式 `node 构建657_关卡内UI.mjs --apply --out=<路径>` 才会写入；**本轮没有执行过 `--apply`**。
