# 工作约定：**能直改控件的事，不要用脚本做**

> 来源：用户 2026-09-29 的要求。
> 原话：「你既然有能力直接编辑控件，有些能直接通过编辑控件完成的工作就不必靠脚本执行了，
> 就像添加文本、删除控件这类问题，直接调整控件就能轻易完成，从脚本执行却需要大量环节……
> 这是效率和稳定性都不高的操作方式」

---

## 一、为什么

我这边有两条改动通路：

| 通路 | 我怎么做 | 生效环节 |
|---|---|---|
| **A. 直改控件** | 用 `tools/gil/*.mjs` 直接读写 `.gil` 的控件记录 | **1 步**：改文件 → 你在编辑器里导入 |
| **B. 改脚本** | 改 Lua → 打包 → 内嵌进 `.gil` → 同步沙箱 | **N 步**：脚本加载 → 找控件 → 设属性 → 每帧渲染维持 |

**B 的每一环都可能出错**，而且错了以后症状往往不在出错的地方。

### 这次的真实教训（删三个工具按钮）

我走的是 B，结果连踩四轮：

1. 把三个按钮**从布局表里不 push** → 按钮**还在屏幕上**
   （渲染的差集逻辑**只隐藏"曾经显示过"的控件**，从没进过计划的不会被隐藏）
2. 改成 `visible = false` 留在计划里 → 才藏掉
3. 你手动把控件删了 → 脚本 `sub(id,"label")` **找不到子控件** →
   真机日志刷出 16 条"读回 nil"（**不是写入失败，是控件不存在**）
4. 再把布局表里的声明删掉 → 才真正一致

**同一件事，A 通路只需要"删掉记录"一步。**

---

## 二、判定表：这类事走 A，那类事走 B

### ✅ 走 A（直改控件）

| 事情 | 做法 |
|---|---|
| **删控件** | 删记录 + 从父控件的子列表里摘掉（`tools/gil/` 现成工具） |
| **加控件** | 克隆一个已知可见的原型 + 改名 + 改父子关系 |
| **改位置 / 尺寸** | 直接改记录的几何字段（或你在编辑器里拖） |
| **改图片** | 成对改 `imageSource` + `imageId`（**只改 id 会"属性变了画面没变"**） |
| **改层级** | 改父控件子列表里的顺序 |
| **改子控件顺序 / 归组** | 同上 |

### ⚠️ 走 B（必须脚本）

| 事情 | 为什么不能走 A |
|---|---|
| **文字内容** | 存档里**读不到文字**（`ruler.c.1` 显示 "C1"、`hud.title` 显示标题，但记录里只有控件自己的名字）。目前**只能运行时由脚本写**。 |
| **运行时生成的东西** | 格子（`cell.r.c`）是按模板在运行时建的，存档里没有 |
| **随状态变化的显示** | 头像换图、✗ 显隐、墙门显隐、进度文字 |
| **按人数自适应** | 头像卡列数、行标列标对齐 |
| **交互逻辑** | 点击/双击/长按/键盘 |

### 🤝 两者都能做时，默认选 A

例如"按钮该显示什么文字"：**文字内容走 B**（存档存不了），
但**字号 / 位置 / 对齐 / 尺寸走 A**（你在编辑器里调，脚本不许覆盖）。

> 这正是 `cfg.respect_editor_rect`（默认 `true`）的由来：
> **存档里已有的控件保持编辑器几何，脚本只摆自己运行时生成的控件。**

---

## 三、走 A 时的纪律

1. **先备份**（`git` 提交，或 `tools/restore_backup.ps1` 快照）
2. **改完立刻回读验证** —— 不要只看"写成功了"，要**重新解析文件**确认结构没坏
3. **尾标记 `0x00000679` 必须在**（`tools/gil/*.mjs` 一般会检查）
4. **别拿"运行时状态为假"的控件当克隆原型**
   （例如墙/门在存档里是 `visible=false`，克隆出来的副本也是隐藏的）
5. **图片必须成对改** `source` + `id`

---

## 四、走 B 时的纪律（仍然适用）

1. **改完必须重打包 + 重内嵌**，否则你跑的是旧脚本
2. **脚本不要再"接管"编辑器里已有的几何**
3. 给脚本加开关时放在 **`cfg` 顶层**（不是 `cfg.cells` 里）
4. 断言要锁**用户可感知的行为**，不要锁**内部机制**
   （本项目已经因此红过三次：`erases`、`pending_click`、`action.q.x`）

---

## 五、给未来的我：动手前先问一句

> **这件事，能不能只改 `.gil` 就完成？**

如果能 —— **就只改 `.gil`**，别去动 Lua。
脚本的职责是**运行时才成立的东西**，不是静态布局。

## 六、★ 复用现成机制前，先 grep 它的**所有**读取方

> 来源：2026-09-30。这条是我这几轮里**最贵**的一次教训，单独记下来。

### 事情经过

房间名标签要"每帧按房间外框摆位置"，而适配器有一条现成通道：
`self.instantiated[id]` 为真 ⇒ **跳过 `respect_editor_rect`**（编辑器几何优先）⇒ 脚本的 rect 生效。

看起来**正好是同一个语义**，于是我直接复用：

```lua
adapter.instantiated[n.id] = true     -- ❌ 我第一版这么写的
```

**结果**：`instantiated` 还管着**别的**事 —— 它表示"这个控件是脚本用 Instantiate 建的"，
因此**允许被 `DestroyClientUIControl` 真销毁**。
于是房间标签/选卡色块在某次渲染里短暂不可见时，被判为"该隐藏" ⇒ **真销毁** ⇒ 再也回不来。

**症状的迷惑性**（这是最值得记的部分）：

```
play_test 报：可见色块 0 块
单独探针看：  room.1/2/3 visible=true（3 块）
```

同一个功能，**两处看到的不一样**。我先怀疑"快照太早"，试了重取状态、试了轮询重试，
**都不管用** —— 才回头去 grep `instantiated` 的其它用途。

### 结论（下次照做）

1. **一个布尔标记往往不只表示一件事。** 复用之前，`grep` 它的**每一处读取**，
   逐个问"我这次改动会不会在这里产生副作用"。
2. **优先新增一个语义单一的小标记**，而不是借用"看起来差不多"的现成标记。
   （正解是 `runtime_rect`：**只跳过位置检查**，不碰销毁语义。）
3. **"同一功能两处观察结果不一致" ⇒ 优先怀疑状态被别处改过**，
   而不是怀疑采样时机。我在这上面浪费了好几轮。

### 同一个 bug 形状（都记在这里，别再犯）

| 形状 | 表现 | 教训 |
|---|---|---|
| 同名概念**多处定义** | 改一处另一处不变（`erases` 动效、缩放表、关卡清单、`hud.progress`） | 只留**一处定义** |
| 复用**多义标记** | 本 bug（`instantiated`） | 先 grep 全部读取方 |
| **`and nil or`** | `x and nil or y` 恒为 `y` ⇒ 逻辑永远走另一支 | 含 nil/false 的分支写**显式 if** |
| `pairs` 遍历里 `nil` = 键不存在 | "清空"语义永远下发不了（`obj`/`image`/`object`） | 清空用 **`false` 哨兵** |
| **断言锁死实现** | 实现一变测试就红，误报成 bug | 只锁**用户可感知的行为** |
| 用自己的解析器验证自己写的文件 | 循环论证 —— "往返无损"查不出真问题 | 拿**编辑器认可的文件**当模板逐字段对齐 |
