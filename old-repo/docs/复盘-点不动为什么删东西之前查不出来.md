# 复盘：「点不动」为什么在删东西之前查不出来

> 2026-10-02 深夜记。基于当天的 ~60 条提交、真机日志、以及 `93.gil`（重建前）与 `97.gil`（重建后）的对照。
>
> **一句话结论**：这个 bug **一直存在**，但被「旧控件恰好还在」**掩盖**了 ——
> 它只在**外部结构变化**（控件被删/改名）时才暴露，**而我在整个调试期间都默认"结构不变"**。

---

## 一、这个 bug 的真身

**⇒ 三处「把控件名写死」的就绪判据 / 名单**：

| # | 位置 | 写死的名字 | 后果 |
|---|---|---|---|
| 1 | `engine_adapter` 的 `MANAGED` / `CURSOR_CONTAINERS` | `home` / `select` **不在名单里**（后来补了，又索引写错数组） | **门控②不生效** ⇒ 子控件收不到点击 |
| 2 | `entry_client_script.lua` 的 `probe_or_dump()` | `board` / `cell.1.1` | **判据永久为假** ⇒ 一直重试 |
| 3 | `main.lua` 的 `Murdoku.on_start()` | 同上（**同一个判据的第二份副本**） | **`on_start` 永远返回 nil** ⇒ **主页/隔断/一切设置全不执行** |

**⇒ 只有第 3 处会"爆炸"**（因为它让整个开局流程不执行）—— **而它的触发条件是**：
**`board` / `cell.1.1` 从 `.gil` 里消失**。

---

## 二、为什么"删东西之前"查不出来

### 2.1 掩盖机制（这是核心）

```
【重建前 93.gil】
  .gil 里有 board / cell.1.1
      ⇒ 判据 `find("board") or find("cell.1.1")` **为真**
      ⇒ on_start 正常执行
      ⇒ 主页可见性、seal_containers（隔断）**都设对了**
      ⇒ 判据硬编码的缺陷**完全不可见**（它只是"恰好"写对了）

【重建后 97.gil】
  board / cell.1.1 被删除
      ⇒ 判据**永久为假**
      ⇒ on_start 永远返回 nil
      ⇒ 主页 vis=false（消失）+ 隔断没设（失效）
      ⇒ 症状**爆炸式**出现 ⇒ 反而**立刻**定位到
```

**⇒ ⇒ 这不是"删了才引入的 bug"，而是"删了才**可见**的 bug"** ——
**它靠外部结构"恰好没变"来维持正确性**，属于**隐藏耦合**。

### 2.2 为什么调试期间我一直没碰到触发条件

**⇒ 因为我的调试方式**默认结构稳定****：

| 我的默认假设 | 实际风险 |
|---|---|
| **控件名不变**（`board`/`cell.1.1` 永远在） | 用户在编辑器里随时会改名/删除 |
| **同名控件只有一个** | 模板引用、副本、实例都可能同名 |
| **"找到某个控件"= "树就绪"** | 树可能部分就绪/结构已变 |
| **失败会被打印出来** | `pcall` 吞错、`if` 跳过、`return nil` 全都不打印 |

**⇒ 第 4 条最致命**：**这个 bug 全程**静默**** ——
`on_start` 返回 `nil` **不打印**、`probe_or_dump` 重试**不打印** ——
**用户看到的是"干干净净无事发生"**，我只能靠**逐轮加探针**把它一层层剥出来（最后是靠 `safe_on_start` 强制打印三种结局才定死）。

## 三、同一个模式当天犯了 **3 次**（说明它是系统性的，不是手滑）

| 次数 | 位置 | 症状 | 白跑的轮次 |
|---|---|---|---|
| 1 | `MANAGED` 名单漏 `home`/`select` | 门控②不生效 | ~3 轮 |
| 2 | `CURSOR_CONTAINERS` 索引写成 `MANAGED[i]`（边界与取值不是同一个数组） | 名单"补了"却完全没生效 | ~2 轮 |
| 3 | `probe` 判据写死 `board`/`cell.1.1`（**两个文件各一份**） | 主页消失 + 隔断失效 | ~4 轮 |

**⇒ 共同形状**：

```
同一个"事实"（受管容器名单 / 就绪判据）
    ├── 在代码里有多份副本
    ├── 每份都硬编码了**具体的控件名**
    ├── 改的时候只改到一份 / 改错索引
    └── 失败时不打印任何东西
```

## 四、技术层面的根因（不只是流程问题）

### 4.1 「就绪」没有单一真相源

**⇒ 每个模块各写一份"树就绪了吗"**：

- `entry_client_script.probe_or_dump()` 一份
- `Murdoku.on_start()` 又一份
- `Adapter:ensure_cells()` 里还有"参照格子存在吗"

**⇒ 三份判据、三套名字、没有共享函数** ⇒ **必然漂移**。

### 4.2 失败路径静默

**⇒ 项目里"放弃/跳过"的路径**几乎都不打印**：

```lua
if adapter.ensure_widgets then ... end        -- 不满足就整段跳过，一行日志都没有
local ok, obj = pcall(game.Instantiate...)    -- pcall 吞掉 true error
if probe == nil then return nil end           -- 返回 nil，不打印为什么
```

**⇒ 我在当天至少 3 次因此白跑**（"四个按钮没出现"那次最典型：代码在、位置对、**但整段被 `if` 跳过、连一行日志都没有**）。

### 4.3 一次改多个变量 ⇒ 结论互相污染

**⇒ 最典型的一次**：为了验证"容器由藏变显会不会让射线失效"，
我**同时**把 `home` 和 `select` 都设成"恒可见" ⇒ **`home` 盖住了 `select`** ⇒
实验**必然失败** ⇒ 我把结论写成"由藏变显不是原因"—— **其实那轮什么也没证明**。

### 4.4 用单一样本推断全局

**⇒ 我读 `home`（容器）的 `raycastTarget` 得到 `nil`** ⇒ **就断言"这个字段在引擎里不存在"** ⇒
**而它其实是**按钮**的字段（`预设按钮` 三个自有字段之一）** ⇒
**接着 5 轮都在错误的方向上找"为什么点不动"**。

### 4.5 文档里早有答案，但我先猜后查

**⇒ 当天上午真正的正解（`raycastTarget`）**写在项目自己的两份文档里**：

- `docs/最小骨架控件清单.md:151`：「**可被光标射线检测**（`raycastTarget`）—— 关掉就点不动」
- `docs/真机-cell.1.1-逐步指南.md:67`：「**界面看得见，但点哪儿都没反应**」（**一字不差的症状描述**）

**⇒ 我绕了 16 轮才去读它们**。

## 五、可操作的改进（按"能不能立刻做"排序）

### A. 立刻做（当天就能落地）

| # | 做法 | 解决什么 |
|---|---|---|
| A1 | **把"就绪判据"收进一个函数**（`Adapter:is_tree_ready()`），所有调用方都用它 | 消掉多份副本 |
| A2 | **每一条"放弃/跳过/返回 nil"的路径都打印一行**（含条件值） | 消掉静默失败 |
| A3 | **所有"名字清单"集中定义一次**（`MANAGED` / `CURSOR_CONTAINERS` 这类） | 消掉"改一处漏一处" |
| A4 | **凡"改了属性"必回读并打印**（`showCursor` / `raycastTarget` 都靠这个才查清） | 消掉"改了没生效" |

### B. 流程上（下次遇到"看不见/点不动"时的顺序）

| # | 顺序 | 为什么 |
|---|---|---|
| B1 | **先读项目自己的排查清单**（`docs/最小骨架控件清单.md`、`docs/真机-*.md`） | 答案常在里面 |
| B2 | **再让失败可见**（加打印），**不要先改行为** | 否则在猜 |
| B3 | **一次只改一个变量** | 否则结论污染 |
| B4 | **用"能用的样本"对照"不能用的样本"**，逐字段比 | 这是用户提的方法，一次就定位到了 |
| B5 | **问"现象有什么可观察的差异"**（音效/光标/有没有反应） | 用户三次凭这个把方向拉正 |

### C. 结构上（重建之后要守住的）

| # | 原则 |
|---|---|
| C1 | **编辑器里只留最少的东西**（`home` + `stage` + 模板引用），其余**全部脚本创建** —— 重建后的 `97.gil` 就是这个形状 |
| C2 | **"外部结构变化"必须被当作一等公民**：判据只认**结构不变量**（如"root 有 >3 个子控件"），不认**具体名字** |
| C3 | **脚本创建的控件自带 id**（`selbtn.N` / `cell.r.c`），**不依赖编辑器命名** |

## 六、附：`93.gil` 与 `97.gil` 的对照（为什么留 93 有价值）

| | `93.gil`（重建前） | `97.gil`（重建后） |
|---|---|---|
| **编辑器控件** | `home` / `select` / `board` / `left` / `right` / `topbar` / `toolbar` / `modal` / `intro` / `assets` … | **只留 `home` + `stage` + 三个模板引用** |
| **判据（写死 `board`/`cell.1.1`）** | **恰好为真** ⇒ bug 被掩盖 | **永久为假** ⇒ 症状爆炸 ⇒ 立刻定位 |
| **对调试的意义** | **"查不出来"的现场**（保留它，才能复现"当初为什么看不见"） | **"一删就现形"的现场**（证明是隐藏耦合，不是新引入的） |

**⇒ 建议两份都留在仓库里**：
- **`93.gil`** = **"掩盖态"的证据**（以后改判据时，可以拿它验证"结构变了会不会炸"）
- **`97.gil`** = **"暴露态"的证据**（新基线）

**⇒ 判断标准（从这次学到的一句话）**：

> **如果一个 bug 只在"我没动过的东西"里才查不出来，
> 那它不是查不出来，而是**我一直在依赖那个东西恰好没变**。**
