fix: measure the long press with the engine's own frame time, not any clock.

The user reported this twice and the second report was the one that mattered: placement n+1 still
needs a longer hold than placement n. My v184 fix swapped one clock for another and the shape of
the bug never changed, which is the clue I should have read the first time. Both clocks fail for
the same reason -- neither runs at the same rate as real time.

self.now is the total accumulated since the level started, so reading it at two different moments
is scaled by however many frames elapsed. os.clock is CPU time, and a game spends most of its
wall time waiting on frames, so it advances slower than real time -- and by a ratio that shifts as
the board fills and each frame gets busier. That ratio change is exactly "the more you place, the
longer you must hold". My earlier reasoning stopped at "it is monotonic, that is enough"; monotonic
only guarantees it never goes backwards, not that one second equals one second.

The duration now comes from neither clock. The engine hands us dt every frame, and while a press
is live the tick adds those up, so the number is literally how long the finger was down. This is
what game engines do. It cannot reintroduce the old drift because the accumulation starts at the
press and lives only inside one gesture, where the anchor problem does not exist. os.clock stays
only as a fallback for a press that outlives its ticks, and it is the same source as the timestamp
so the two cannot disagree.

One ordering bug of mine surfaced immediately: on_cell_up cleared _press before measuring it, and
the measurement reads from _press, so every long press failed. Caught by the suite.

input_logic now drives holds by advancing frames, because that is what the code reads, and gains
the regression that matters: hold 0.50s and it places, hold 0.30s and it does not, then play sixty
seconds of frames and repeat both -- identical results. Any clock that is not wall-rate fails that
third check. I verified it by making the criterion fall back to a clock difference and running
that clock at a quarter speed, which is the device's CPU-clock situation: seven assertions go red.

Two process lessons worth keeping, both from this round. A sabotage that breaks syntax does not
test anything -- the bundle fails, the old artifact runs, and the script reports "sentinel
ineffective" when the truth is "nothing ran". And a sabotage must be confirmed to have reached the
artifact before its result means anything; my first attempt checked for the slow clock inside the
bundle when the slow clock lives in the test file. tools/verify_longpress.mjs now asserts both
reachability and syntax before running, covers both break points, and restores byte-for-byte.
