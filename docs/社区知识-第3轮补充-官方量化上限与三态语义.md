## 2. ★★★ 新答案：「改了 visible 又被改回去」的**官方机制**

主文件 §2.6 结论是「有记载，但**不是被引擎复位**」，并列了四个替代成因；§8.2 仍把
「引擎把 `visible` 复位」列为**零来源**。**本轮找到了官方机制，可以定案。**

### 2.1 官方原文：《界面控件组》`mhg1700h8bug` 第二节「界面控件组状态」

- 官方 URL：<https://act.mihoyo.com/ys/ugc/tutorial/detail/mhg1700h8bug>
- 本工程离线副本：`docs/api-cache/mhg1700h8bug.txt:17-50`（逐字一致）

> **(1) 界面控件组_状态_：激活、未激活**
> - **激活** 存在于界面布局，可通过节点图管理表现状态
> - **未激活** **不存在于界面布局，不可操作表现状态**
>
> **(2) 已经激活的界面控件组_表现状态_：开启、关闭、隐藏**
> - **开启**，界面控件组可见性开启。
>   - 隐藏状态到开启状态，将界面控件组可见性开启。
>   - **关闭状态到开启状态，将界面控件组重新初始化，并开启可见性**
> - **关闭**，界面控件组可见性关闭，**并且不保留动态改动的信息**
>   - **关闭后开启的界面控件组，表现和数据都会初始化**
> - **隐藏**，界面控件组可见性关闭，**并且保留动态改动的信息**
>   - **隐藏后开启的界面控件组，表现和数据都和隐藏前的一致**

### 2.2 与节点语义对齐（官方《执行节点》）

「设置界面控件(组)状态」节点，**归属端：服务端**，参数「显示状态」枚举：

> **关闭：不可见且逻辑不运行**
> **开启：可见+逻辑正常运行**
> **隐藏：不可见+逻辑正常运行**

### 2.3 结论（可直接替换主文件 §2.6 的成因清单）

- **【官方】** 「改了 visible 又被改回去」**不是**引擎周期复位，而是**状态迁移**导致的**重建/初始化**。
- **【官方】** 判据：
  - 走了 **关闭 → 开启** ⇒ **表现和数据都会初始化** ⇒ 你设的 visible/文本/位置**全丢**。
  - 走了 **隐藏 → 开启** ⇒ **保留动态改动** ⇒ 你设的值**还在**。
- ⇒ **【推断】** 本项目 `face`「被引擎关掉又要每帧点亮」的现象，**优先怀疑**：
  该控件所属路径被走了「关闭」语义（或落在**未激活**的控件组里 —— 未激活时**根本不在界面布局中**，
  更不可能被脚本按索引拿到）。**验证方法见 §8 的 X4。**

### 2.4 附带：官方 FAQ 对「初始可见性」的定性

《界面控件组管理》`mhewyi0fjfvs` 与《界面控件》`mhnapxrumtzy` 都列了「**初始可见**」参数：

## 3. ★★ 新答案：层级 / 排序 —— 官方承认「曾经不生效」，并提供两种渲染模式

主文件 §2.4 讲的是「同层绘制顺序的两套规则」；本轮补的是**官方层面**的机制变更。

### 3.1 官方原文：《界面控件》`mhnapxrumtzy` 第四节「界面控件的渲染模式」

- 官方 URL：<https://act.mihoyo.com/ys/ugc/tutorial/detail/mhnapxrumtzy>
- 本工程离线副本：`docs/api-cache/mhnapxrumtzy.txt:227-250`

> 「**在月之五及之前的版本中，界面控件的渲染仅和创建时序有关，层级参数并未生效。
> 在月之六版本我们对其进行了修复**，并提供了两种渲染模式，分别为【时序渲染(旧)】和【层级渲染(新)】，
> 可以在界面控件组管理中图示位置点击进行切换」
>
> **时序渲染(旧)**：原有的渲染逻辑，该模式下将按照"界面控件"**创建时序**进行渲染。
> **月之六版本更新前创建的关卡存档、已发布的关卡均默认为该模式**。
> 如果需要对控件进行修改，那么**新增的控件可能会出现层级显示的问题**，建议切换到【层级渲染(新)】模式；
> 如果不需要对控件进行修改，可以保持该模式。
>
> **层级渲染(新)**：月之六版本新增的渲染逻辑，该模式下"界面控件"将会按照**层级配置顺序**进行渲染，
> 支持对界面控件层级进行调整。**月之六版本更新后新创建的关卡存档将默认为该模式**。
>
> **此外，请注意后续版本将不再维护新增控件在【时序渲染(旧)】模式的表现**，
> 建议奇匠们在月之六版本更新后均使用【层级渲染(新)】模式进行制作。
>
> **【时序渲染(旧)】模式切换到【层级渲染(新)】模式后，推荐的修复方式：**
> - **检查层级配置，层级越大越靠上；同层级的会按照创建时序排列，后创建的在上**
> - **层级渲染模式下，界面布局中的控件层级低于界面控件库中激活的控件层级**，
>   若原先是通过节点的创建时序实现主屏控件显示在控件模板上层的话，**推荐都转为控件模板，然后通过层级配置实现**

### 3.2 结论

- **【官方】** 层级语义：**数值越大越靠上；同层级按创建时序，后创建在上**。
  （与官方 API `SetSiblingIndex`「**数值越大通常越靠后、显示越靠上**」方向一致。）
- **【官方】** 「层级设了不生效」**有官方解释**：存档是**时序渲染(旧)**。
- **【官方】** 官方**已宣布不再维护**旧模式下的新增控件表现 ⇒ **新工作应统一用【层级渲染(新)】**。
- ⇒ **【推断】** 若本项目/真机存档是**月之六之前创建的**，它是**时序渲染**，此时
  「层级」参数**不可靠**，只能靠**创建/实例化顺序 + `SetSiblingIndex`** 控制前后。
  **这条能解释"层级明明设了却不生效"的历史记录。**

（补充官方字段：《界面控件》通用数据配置里 `层级`「**数字越大显示层级越高**」，
`锚点设置`「**在屏幕分辨率改变时，会以锚点继承相对位置**」。）

## 4. ★★ 新答案：`active` / `visible` 是**只读字段**，必须用方法

主文件 §3.4 讲了 `active` 默认为 false。本轮补两点更硬的：

### 4.1 官方字段表（`mhtakr07vej4` §13.(1)）

| 字段 | 类型 | **访问** | 官方说明 |
|---|---|---|---|
| `alive` | boolean | **只读** | 控件是否存活 |
| `id` | integer | **只读** | 运行时ID |
| `prefabIndex` | integer | **只读** | 控件模板索引 |
| `active` | boolean | **只读** | 激活状态；`true` 时控件**可见且挂载脚本逻辑运行**，`false` 时控件**不可见且脚本逻辑停止运行**。**默认为 false。** |
| `activeInHierarchy` | boolean | **只读** | **计入全部父级后**的实际激活状态 |
| `visible` | boolean | **只读** | **仅控制可见性，不改变激活状态或脚本逻辑运行状态** |
| `name` | string | 读写 | 控件名称 |
| `parent` | ClientUIBaseControl | 读写 | 父控件 |

- ⇒ **【官方】** `active` / `visible` **都是只读** ⇒ 写 `ctrl.active = true` 或 `ctrl.visible = true`
  **不可能生效**（模拟器真机观察补充：写未声明字段报 `cannot set <field>, no such field`）。
  **必须**用 `SetActive(...)` / `SetVisible(...)`。
- ⇒ **【官方】** **`SetActive(false)` 会停脚本**；`SetVisible(false)` **不停**。二者语义不可互换。
- ⇒ **【官方】** `activeInHierarchy` 是"计入全部父级"后的**真实**状态 ⇒ 排查"我设了 true 还是不显示"时，
  **应该读 `activeInHierarchy` 而不是 `active`**（父级关着，自己的 `active` 仍是 true）。

### 4.2 与模拟器真机观察的差异（保留双方口径）

**【社区经验·模拟器】** `1475505/miliastra-beyond-simulator`，
[`client/lua-runtime/docs/observed-contract.md:7`](https://github.com/1475505/miliastra-beyond-simulator/blob/master/client/lua-runtime/docs/observed-contract.md)：

> 「`ClientUIBaseControl.active` **官方加工稿写「默认为 false」**。
> **真机未改过的客户端模板实例为 `true`**；明确 false 的模板实例为 `false`。
> 编辑器 Authoring 新建节点默认 true。**runtime spec 省略该字段时仍按 false（手写树）**，
> compile 带入编辑器保存值。」

- ⇒ **综合结论**：
  - **编辑器里建的**客户端控件模板实例 → 真机实测默认 **`true`**（与官方"默认 false"不一致）。
  - **手写/程序生成**（省略该字段）→ 按 **`false`**。
- ⇒ **【推断】** 「同一份 Lua，编辑器里正常、程序生成的存档不显示」**是预期行为**。
  本项目 `entry_client_script.lua:174` 的构建标记已写「手写树漏写 active 会少一层可见性」——**方向正确，建议保留并写进规范**。

### 5.1 关于「网格视窗是否虚拟化」的口径澄清（对第 2 轮勘误的勘误）

第 2 轮 §1 读官方《网格视窗控件》得到「**官方就有虚拟化**，没有 2000 项上限」。
**官方原文确实这么写**，但需要注意它**没有**回答"`RefreshItems` 回调几次"：

> 官方原文（`mhfkrr0i7gds` 第二节「实现原理」）：
> 「网格视窗的列表采用**复用列表结构**，**出于性能考虑，仅会加载处于可见范围内的列表项**。
> - _网格视窗列表发生滚动时：_ 对列表项内容进行**刷新（触发回调）**，
>   可以使用接口 `RefreshItems` 触发，从而实现滚动到对应位置时，显示准确列表项内容的效果。」

而官方 API 对 `RefreshItems` 的描述是：

> `RefreshItems(itemCount, refreshCallback)` — 「**刷新列表项并逐项调用回调**；
> 刷新回调形式为 `fun(control: ClientUIBaseControl, index: integer)`」

- **【官方】** 两条**都成立**，但**官方没有明说**"逐项"是**全部项**还是**仅可见项**。
- **【社区经验·模拟器】** MBS 的实现是「**同步为全部项调用**；**没有可见区虚拟化，最多 2000 项**」

  1. **列表项内容必须由 `RefreshItems` 回调填**（因项被复用，滚动后不填会显示上一项残留）。

### 6.1 【官方】`fontSize` 必须是整数 —— 社区有**真机报错原文**

### 6.2 【官方】按键监听**移除必须用同一回调引用**

`mhtakr07vej4` §13.(5)：
> `RemoveKeyEventListener(eventType, callback)` — 「移除指定按键事件和回调的监听；**回调必须与注册时的引用相同**」
