## 1. ★★ 容器位置口径：交付用 **(0,0)**，不是字面 (800,450)（与 lead 第 1 条不同，证据如下）

lead 要求"容器位置 = (800,450)（画布中心）"。**但 `.gil` 记录里的 `#504` 位置不是画布绝对坐标，而是"相对父级中心"的 anchoredPosition**（引擎 `SetAnchoredPosition` 语义，Y 向上）。本档存量的铁证：

| 控件（root 直接子） | 存档位置 | 它在真机上的实际表现 | 说明 |
|---|---|---|---|
| `modal`（四键弹窗） | **(0,0)**，633×383 | **屏幕正中**（真机多轮验证可用） | 若是绝对坐标，(0,0)=左下角 ⇒ 弹窗应消失；**实际居中** ⇒ 位置是相对的 |
| `home`（主菜单） | **(0,0)**，脚本撑到 1600×900 | 铺满屏幕 | 同上 |
| `settle.btn`（左下结算按钮） | (-642,-380)，217×60 | 盒子左边 ≈ 画布 x=49.5 / 底 ≈ 40 | 800−642=158 中心，450−380=70 中心，与设计一致 |
| `stage`（棋盘） | (100,20)，584×584 | 棋盘中心 (900,470)（仓内文档实测） | 800+100=900，450+20=470 |
| `select.prev` / `select.card.1` | (-724,0) / (-374,-4.5) | 选关屏左右位置正确 | 同上 |

⇒ **两张 1600×900 的容器要"中心 = 画布中心"，记录里就写 (0,0)**。写 (800,450) 会被引擎再加父级中心 ⇒ 容器中心跑到 (1600,900) 画布外，整批控件不可见。
（lead 提到的 `labels` 700×700@(0,0) 偏到屏幕外：按本档口径 (0,0) 正是画布中心；那是**脚本侧给 label 子控件下发的坐标口径**问题，lead 已用 `pos_runtime` 修掉。）

**子控件偏移与 lead 的等价说法完全一致**：
```
数据 x,y（画布像素、左上原点、Y 向下）
→ 子控件在画布上的绝对中心 = (x, 900 - y)（画布 Y 向上）
→ 记录 anchoredPosition（相对容器中心 800,450）= (x - 800, 450 - y)
→ size = (w, h) 像素
```
本工具正是这么写的（`fart.case_001.1`：数据 (788.13,205.19) → 回读 (-11.87, 244.81) = 788.13−800 / 450−205.19 ✓）。

> 若真机实测证明 lead 口径才对：一条命令切换 `--container-pos=center`（把容器位置写成 800,450），子控件换算不变。本轮默认 `zero`。

## 5. 已知风险 / 边界

1. **容器位置口径**：本轮按"存档位置 = 相对父中心"写 **(0,0)**（证据见 §1，`modal`/`home`/`settle.btn`/`stage` 都是这个口径）；若真机显示仍偏移，先 `--container-pos=center` 重跑对比（一次只改一个变量）。
2. **旋转符号**：数据 rot 按"与引擎 `#508/#3` 同号（逆时针为正）"写入；真机若方向相反 ⇒ `--rot-sign=-1` 重跑。旋转是"支持字段"（不是本工具发明的：`gen_tutorial_teach.mjs` 的 `applyRotation` + `docs/转换器-gil到模拟器存档.md:151`）。
3. **控件数 957 < 1000**：两个容器各近 200~256 个子控件，接近"单个界面控件组内控件最大 1000"上限但未超；后续若再加图元需重新算预算。
4. **透明图元**：`imageColor` 的 A 通道按数据写入（很多图元 A<255）；若引擎对 imageColor 的 alpha 乘算有差异，观感会偏淡/偏浓 —— 属素材/引擎表现，不是结构问题。
5. **根顺序/遮挡**：`fart.*` 在 root 里位于 `labels` 之后、`home` 之前 ⇒ 画在棋盘/墙线之上、菜单之下（符合"家具压墙线"）。
6. **两份容器都 visible=false**：切关由适配层 `baked_level` 分支控制；若真机不显示，先查 `find("fart.case_001")` 是否命中（名字精确匹配已保证）。
7. 本轮**未真机验证**（只做结构 + 离线断言）。
