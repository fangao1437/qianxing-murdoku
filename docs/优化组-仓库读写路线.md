## 3. 路线 A（★ 推荐 ✓ 今天就能用 ✓ **不需要 git** ✓）

### 3.1 桥接方：导出快照给优化组
```powershell
cd "D:\新建文件夹\miHoYo Launcher\qianxing-murdoku"

# ★ 先看状态（远程/分支/HEAD/跟踪文件数/漂移/git 有没有 ✓）
node tools/repo_bridge.mjs status

# ★★ 裁剪导出 —— ★ 别整包（967 MB ✗）✓
node tools/repo_bridge.mjs export --out="D:\exchange\snap-2026-10-12" --only=lua,tests,tools,docs

# ★ 要单文件就再压一次（Windows 自带 ✓）
Compress-Archive -Path "D:\exchange\snap-2026-10-12\*" `
                 -DestinationPath "D:\exchange\snap-2026-10-12.zip" -Force
```
★ 产出结构 ✓：
```
snap-2026-10-12/
  files/…            ← ★ 与仓库一致的只读副本（★ 只含被跟踪的文件 ✓）
  manifest.json      ← ★ 每个文件的 sha256 ＋ **清单指纹** ＋ 基准提交 ✓
```
★ 把 **`manifestId`（如 `43c014a951580e9d`）** 一起告诉优化组 ✓ —— ★ 以后引用版本就用它 ✓

### 3.2 优化组：怎么读
1. ★ 解压到**任意可写目录** ✓（★ 不要在仓库里改 ✗）
2. ★ **核对指纹** ✓：
   ```powershell
   node tools/repo_bridge.mjs verify --from="<解压目录>"
   #   ★ 应当报 "无差异 ✓" ✓ —— ★ 若报差异 ⇒ 包在传输中被改过 ✗
   ```
3. ★ 正常改代码 ✓（★ 想跑回归就按第 5 节 ✓）

### 3.3 优化组：怎么交回
★ **什么都不用特殊做** ✓ —— ★ 直接把改完的目录**整个交回** ✓（★ 保留 `manifest.json` ✓）
★ 回话时带上 ✓：★ **基于哪个指纹** ＋ ★ **改了哪些文件** ＋ ★ **跑过哪些回归** ✓

### 3.4 桥接方：收包 → 验证 → 应用 → 推送
```powershell
# ★ ① 看差异（★ 只读 ✓）
node tools/repo_bridge.mjs verify --from="D:\exchange\snap-回包"

# ★ ② 演练（★ 默认只演不写 ✓ 退出码 3 ✓）
node tools/repo_bridge.mjs apply  --from="D:\exchange\snap-回包"

# ★ ③ 确认无误 ⇒ 真的应用 ✓
node tools/repo_bridge.mjs apply  --from="D:\exchange\snap-回包" --yes

# ★ ④ 过闸门（见第 5 节 ✓）之后再提交
git add -A
git commit -m "…"          # ★ 规范见第 6 节 ✓
git push origin master
```
★ **安全的默认值** ✓：★ `apply` **不带 `--yes` 时一个字节都不写** ✓（★ 已实测 ✓：演练后工作区文件哈希未变 ✓）

## 4. 路线 B（★ 若优化组自己有 git ✓ 更省事 ✓）

★ 这时用 **`git bundle`** ✓ —— ★ **一个文件装下整段历史** ✓，★ 可 `clone`／可增量 ✓，**不需要 GitHub** ✓。
★ 比 zip 好在 ✓：★ **带提交历史** ✓、★ **能算差异** ✓、★ **能双向** ✓。

```powershell
# ── 桥接方：做一个只读 bundle 给优化组（★ 需要桥接方有 git ✓）──
git bundle create D:\exchange\repo.bundle master
node tools/repo_bridge.mjs status        # ★ 记下 HEAD 与漂移 ✓ 一并告知

# ── 优化组：从 bundle 克隆（★ 不需要 GitHub ✓）──
git clone D:\exchange\repo.bundle work
cd work
git remote -v                            # ★ 只有本地路径 ✓ 天然碰不到 GitHub ✓

# ── 优化组：改完 → 建分支 → 打包回传（★ 只打"新增的提交" ✓）──
git switch -c opt/头像-单射修正
git add -A && git commit -m "…"
git bundle create D:\exchange\back.bundle master..opt/头像-单射修正

# ── 桥接方：收下并合入（★ 仍然不碰网络 ✓）──
git fetch D:\exchange\back.bundle opt/头像-单射修正:opt/头像-单射修正
git switch master && git merge --no-ff opt/头像-单射修正
git push origin master                   # ★ 只有这一步需要 GitHub 权限 ✓
```
★ 若只在**同一台机器**上协作 ✓：★ 连 bundle 都可省 ✓ —— ★ 直接 `git clone <仓库路径>` ✓，
★ 优化组在自己的克隆里提交 ✓，★ 桥接方 `git fetch <那个克隆>` ✓ 即可 ✓。

## 8. 常见问题

**Q：优化组能不能只读、不要写权限？**
★ 能 ✓ —— ★ 路线 A 的快照就是**只读**的 ✓；★ 回包由桥接方决定收不收 ✓。

**Q：为什么不用 `gh` CLI？**
★ 一样要**凭据 ＋ 网络** ✓，而且本机连 `git` 都没有 ✗ ⇒ ★ 不解决"优化组无权限"这个根本问题 ✓。

**Q：仓库太大，能不能只给 `lua/`？**
★ 能 ✓ —— ★ `--only=lua` ✓（★ 实测 `--only=lua,tests` ⇒ **54 个文件 / 1.8 MB** ✓）。
★ 但 ★ **别只给 `lua/`** ✗ —— ★ 改完跑不了回归 ✓（★ 至少带上 `tools/`、`tests/` ✓）。

**Q：回包里多出/少了文件怎么办？**
★ `verify` 会**分三类**列出（改／新增／删 ✓）；★ `apply` 会照它执行 ✓。★ 若**新增**了不该进仓库的文件（★ 日志/临时产物 ✗）⇒ ★ 先在 `verify` 阶段剔除 ✓。

**Q：两边同时改了同一个文件？**
★ 本工具**不做三方合并** ✗ —— ★ 它只报差异 ✓。★ 真冲突时 ✓：
★ **桥接方 `apply` 前先 `verify`** ✓，★ 若同一文件双方都改过 ⇒ ★ **不要 apply** ✗，★ 走路线 B（git 能合并 ✓）✓。
