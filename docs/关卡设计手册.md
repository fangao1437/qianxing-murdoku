# 关卡设计手册（偷窃版规则的"数学"）

> 这份文档解决一个问题：**为什么我随手设计的关卡总是不合法 / 不唯一？**
> 下面每条都是从"设计失败 → 推公式 → 改对"的过程里总结出来的，不是理论空谈。
> 配套工具：`lua tools/validate_levels.lua 3`（唯一解校验）、
> `lua tools/dump_level.lua <关卡> out.json`（看实际渲染出来的线索文案）。

---

## 〇、一关最少要有哪些东西

`lua/levels/template.lua` 是骨架，必填的是：

```lua
size = { rows = 5, cols = 5 },           -- 必须是正方形（见 1.1）
walls = { {"h", r, c}, {"v", r, c}, ...},-- 区域边界
doors = { {"h", r, c}, {"v", r, c}, ...},-- 跨区域通道（定义"相邻"）
suspects = { {id="A", name="..."}, ... },-- 人数 == rows（见 1.1）
victim = { id = "V" },
roles = { thief = "D", accomplice = "C" },   -- accomplice 不写 = 本案没有同伙
solution = { A = {r=,c=}, ... },         -- 必须**包含受害者**
clues = { ... },                          -- 见第四节
meta = { false_clue = N, announce = "one" },
rules = { one_per_row=true, one_per_col=true, place_all=true, tie_policy="forbid" },
```

## 一、三条硬性计数约束（不满足直接报错）

### 1.1 棋子数 = 行数 = 列数

```
#suspects == rows == cols
```

5×5 就恰好 5 枚棋子（含受害者），6×6 就 6 枚。
**不是"最多"是"恰好"** —— 因为 `place_all = true` 要求全部摆上，
而 `one_per_row` / `one_per_col` 要求每行每列恰好一人。
于是最终摆位必然是 N 个格子上的**一个排列**。

> 推论：**摆位总数 = N! × N!**（给 N 枚棋子分配 N 行、再分配 N 列）。
> 5×5 → 14400 种，6×6 → 518400 种。这就是为什么求解器在 6×6 上会慢一些。

### 1.2 区域容量 = min(区域行数, 区域列数)

一个区域最多能放几个人，受**它跨了几行、几列**限制：

```
capacity(room) = min(room 覆盖的行数, room 覆盖的列数)
```

因为一人一行一列。**这是设计时最容易忽略的一条**：
一个"2 行 × 5 列"的房间，容量只有 **2**，不是 5。

### 1.3 区域相邻数 ≥ 2

受害者所在区域必须**至少与两个区域门相邻**。
只有一个相邻区域时，"挑无辜人数最多的那个"永远自动成立，
玩家不需要做任何比较，R3 就退化成一句废话。

## 二、R3 / R4 能不能同时满足：先算一遍再动手

设：

```
Rv        = 受害者所在区域
Adj(Rv)   = 与 Rv 门相邻的区域集合（至少 2 个）
Rt        = 盗窃者所在区域 ∈ Adj(Rv)
inno(X)   = X 内"既不是盗窃者也不是同伙"的人数
k         = Rv 内的人数（含受害者）
```

要求：

```
① Rt ∈ Adj(Rv)
② inno(Rt) > inno(X)   对所有 X ∈ Adj(Rv) \ {Rt}     ← 严格最大，不许并列
③ k ≥ 2  ⟹  必有同伙，且 room(同伙) = Rt
④ k = 1  ⟹  同伙可有可无（但若有，仍须与盗窃者同区）
```

### 2.1 关键不等式

把无辜人数记成 `a`（在 Rv）、`b`（在 Rt）、`c`（在其它相邻区域），
无辜总数 = 棋子数 − 1（受害者） − 1（盗窃者） − [有同伙 ? 1 : 0]。

- **k ≥ 2（必有同伙）**：`a ≥ 1`，`a + b + c = 无辜总数`
  且要求 `b > c`。
- **k = 1（无同伙）**：`a = 0`，`b + c = 无辜总数`，要求 `b > c`。

### 2.2 6×6 / 6 枚棋子的具体结论（case_002 就是这么定的）

有同伙时无辜总数 = 6 − 1 − 1 − 1 = **3**。
`a ≥ 1`、`b > c`、`a+b+c = 3` 的解只有两组：

| a | b | c | 结果 |
|---|---|---|---|
| 1 | 2 | 0 | ✅ 合法（case_002 用的是这组） |
| 2 | 1 | 0 | ✅ 合法 |
| 1 | 1 | 1 | ❌ b == c 并列 |

**注意 c 恒为 0** —— 也就是说：**3 个无辜 + 3 个区域时，必然有一个相邻区域是空的。**
这不是 bug，是计数逼出来的。玩家看到"有一个区没人"其实是有用信息。

> 如果想避免空区，就得**减少相邻区域数**（Adj 只有 2 个时，c 是唯一那个"另一个"），
> 或者换更大的棋盘让无辜人数变多。

### 2.3 5×5 / 5 枚棋子 + k=1（case_001 的情况）

无同伙时无辜总数 = 5 − 1 − 1 = **3**，`a = 0`，`b + c = 3`，`b > c`：

| b | c | 合法 |
|---|---|---|
| 2 | 1 | ✅ |
| 3 | 0 | ✅ |

但**容量**会进一步收紧。case_001 的实际约束：

- R_A（3 行 × 3 列）容量 3 → 放盗窃者 + 2 无辜 → `b = 2`
- R_C（2 行 × 4 列）容量 2 → 放 1 无辜 → `c = 1`
- R_B（受害者独处）容量 = 列数

**先数容量，再数无辜**，两边都满足才继续。

## 三、把"每行每列恰好一人"和区域一起算

这一步是设计时最容易翻车的地方。**列是被区域切开的**：

```
可用列数 = 各区域能提供的、互不重复的列
```

例：case_001 里受害者占 col 5，剩下 4 枚棋子只能用 col 1..4；
而 R_A 只用 col 1..3、R_C 只用 col 1..4 ——
如果 R_A 想放 3 个人，它必须**同时**满足"有 3 个不同行"和"有 3 个不同列"。

> **列容量 = 房间跨的列数**，行容量 = 房间跨的行数，取小的那个。

## 四、线索怎么写才能"唯一解"

### 4.1 为什么"至多一条假话"这么难满足

求解器接受的是：**最多有一条线索在答案上不成立**。
所以一条线索集合要唯一解，必须满足：

```
除答案外的每一个 (摆位 × 角色归属) 组合，都至少违反 2 条线索
（或者：违反假话那条 + 至少违反 1 条真线索）
```

否则"少违反一条"的替代解就会混进来。

### 4.2 一条最省事的配方

**给每个棋子都上"行 + 列"两把锁**。这样任何单枚棋子的移动都会同时违反 2 条线索，
天然满足 4.1。case_001 / case_002 都是这个思路。

### 4.3 身份可以整体互换的坑（**必看**）

用 `@thief` / `@accomplice` 这类**角色别名**写线索时，线索只约束"角色在哪"，
**不约束"谁扮演这个角色"**。于是可能出现：

```
解1：D 是盗窃者、C 是同伙
解2：C 是盗窃者、D 是同伙      ← 只要两人位置也镜像一下，就能满足全部线索
```

**实测**：`case_002` 第一版就踩了这个 —— 求解器报 `找到 2 个解`。
解法是补一条**指名道姓**的身份线索：

```lua
{ type = "not_role", who = "D", role = "accomplice" },   -- 鉴定师不是同伙
```

**规则**：只要你也用角色别名写了"盗窃者/同伙在哪"，就一定要再写至少一条
**用真名**的身份线索来打破镜像。

### 4.4 可用的关系型线索（不要求同行同列）

这几个是最好用的，写出来的文案玩家也读得懂：

| 原子 | 参数 | 文案 | 说明 |
|---|---|---|---|
| `col_offset` | `who, other, d` | 「A 正好在 B 东边 3 列」 | `who.c - other.c == d` |
| `row_offset` | `who, other, d` | 「A 正好在 B 南边 1 行」 | `who.r - other.r == d` |
| `distance` | `a, b, d` | 「A 与 B 相隔 4 步（曼哈顿距离）」 | 曼哈顿距离 |
| `compass` | `who, other, dir` | 45° 方位（`ne`/`nw`/`se`/`sw`） | 不共行也不共列 |
| `abs_col_from` | `who, n, from="right"\|"middle"` | 「在倒数第 1 列 / 正中间那一列」 | |
| `abs_row_from` | `who, n, from="bottom"\|"middle"` | 「在倒数第 2 行 / 正中间那一行」 | |
| `alone_with` | `a, b` | 「A 与 B 单独共处一室」 | 该房间恰好只有这两人 |
| `between` | `who, a, b` | 「A 在 B 与 C 之间」 | 行或列落在两者之间 |
| `same_room` / `different_room` | `a, b` | 同区 / 不同区 | |
| `in_front_of` | `a, b` | 门窗正对的两格 | 需要门/窗 |
| `beside_object` / `on_object` / `only_on_object` | | 家具相关 | 需要有 `objects` |

### 4.5 ⚠️ 四个**永远为假**的线索（别用）

| 原子 | 判定 | 为什么永远为假 |
|---|---|---|
| `left_of` | `a.r == b.r and a.c < b.c` | 要求**同一行**，而 one_per_row 禁止同行 |
| `right_of` | 同上反向 | 同上 |
| `above` | `a.c == b.c and a.r < b.r` | 要求**同一列**，而 one_per_col 禁止同列 |
| `below` | 同上反向 | 同上 |

**要表达"谁在谁左边"就用 `col_offset`**（它不要求同行）。
`case_002` 第一版就是误用了 `left_of` / `right_of`，被校验器抓出来才发现。

### 4.6 假话放在最后一条

`meta.false_clue = N` 是**序号**。把假话写在线索表最后，
N 就等于条数，最好读也最不容易写错：

```lua
meta = { false_clue = 15, announce = "one" },   -- 15 条线索，第 15 条是假的
```

### 4.7 `announce` 怎么选

| 值 | 界面表现 | 适合 |
|---|---|---|
| `"none"` | 顶部显示「线索全部为真」 | 入门关 |
| `"one"` | 顶部显示「线索中有一句假话」 | 常规 |
| `"unknown"` | **什么都不显示** | 进阶（case_001 用的这个） |

## 五、标准工作流

```powershell
$lua = "$env:LOCALAPPDATA\Programs\Lua\bin\lua.exe"

# 1) 先按第二、三节把「空间 + 答案 + 角色」定下来（此时 clues 可以空着）
#    但注意：空 clues + meta.false_clue 会报"超出线索范围"，先把 false_clue 去掉

# 2) 填线索，然后校验
& $lua tools\validate_levels.lua 3

# 3) 想不出线索？用暴力搜索兜底（很慢，可能几十分钟）
& $lua tools\find_clues.lua lua\levels\case_00N.lua 12

# 4) 看看玩家实际会读到什么文案（顺带确认哪条是假话）
& $lua tools\dump_level.lua case_00N tools\sim\out\lv.json
#    然后打开 tools/sim/out/lv.json 看 clue_texts

# 5) 在模拟器里真打一遍，确认能赢
node tools\sim\win_path.mjs --level=case_00N
```

**校验器报错时怎么读**：

| 报错 | 意思 | 怎么办 |
|---|---|---|
| `格式: FAIL - 缺少 roles.thief` | 没写盗窃者 | 补 `roles = { thief = "X" }` |
| `结构: FAIL - 盗窃者不在受害者的相邻区域内` | R3 ① | 挪答案，或加一扇门 |
| `结构: FAIL - 盗窃者所在区域不是相邻区域里无辜人数最多的` | R3 ② | 调人数分布（第二节） |
| `结构: FAIL - 受害者与他人同区（k>=2），必然有同伙` | R4 | 补 `roles.accomplice`，或让受害者独处 |
| `结构: FAIL - 同伙与盗窃者不在同一个区域` | R3 ③ | 把同伙挪进盗窃者的房间 |
| `假话: FAIL（声明 X，实际不成立 [i,j,k]）` | 假话条数/序号不对 | 让答案**恰好**违反声明的那一条 |
| `唯一解: FAIL（找到 N 个解）` | 线索不够或有镜像 | 看 4.3 / 补"行+列"两把锁 |

| 关卡 | 尺寸 | 关键教学点 | 参考 |
|---|---|---|---|
| 入门 | 5×5 | 单击笔记 / 双击放置 / 行列约束 | — |
| `case_001` | 5×5 | **k=1 → 没有同伙**（玩家要自己推出来）；`announce="unknown"` | 8 条线索 |
| `case_002` | 6×6 | **k=2 → 必有同伙**，且同伙与盗窃者同区；`announce="one"` | 15 条关系型线索 |

| 进阶 | 6×6 | `tie_policy="allow"`：相邻区域无辜数并列，R3 只能缩小范围，靠线索定生死 | 需要更多线索 |

## 七、两个**界面容量**硬限制（写关卡时必须知道）

关卡数据放不进界面 = 关卡不可解。这两条由 `tests/ui_math.lua` 自动检查。

### 7.1 线索条数 ≤ `clue_max_visible`（当前 18）

界面上**只生成** `clue.1 ... clue.<clue_max_visible>` 这些控件，
超出的线索**连控件都没有**，玩家只能看到一句「还有 N 条线索」，然后就卡住了。

> 2026-09-26 实测踩到：`case_003` 写了 18 条线索，而当时界面只放 12 行 ——
> 后 6 条玩家根本看不见。
> 要写更多线索：调大 `M.LAYOUT.clue_max_visible` / 调小 `clue_row_h`，
> 然后跑 `lua tests/ui_math.lua` 确认没压到图例。

### 7.2 棋盘 N ≤ 求解器能力（当前 7）

求解器是"回溯 + 角色枚举"，摆位总数 = `N! × N!`：

| N | 摆位总数 | 现状 |
|---|---|---|
| 5 | 1.4 万 | 秒级 |
| 6 | 51.8 万 | 秒级 |
| 7 | 2540 万 | 有了**边搜边剪**之后可跑（4 关合计 28 秒） |
| 8 | 16 亿 | ❌ 会跑不完，不要做 |

**边搜边剪**指的是：一放下棋子就立刻检查"它牵涉到的那些线索"
（只用于**不含角色别名**的线索；带 `@thief` 的线索要等角色定了才能判）。
所以**线索写得越"局部"，剪枝越狠、求解越快** —— 这也间接鼓励你用关系型线索。

### 7.3 界面几何是自适应的，但只有一套

- 格子边长 = 可用边长 ÷ N；头像卡列数 = `max(3, ⌈人数 ÷ 2⌉)`（保证只占 2 行）。
- 编辑器里**只需要按"最挤的那一关"摆一套**，脚本运行时会把格子和头像卡
  **重新摆正**（`Adapter:ensure_cells` / `Adapter:apply_tray_layout`）。
- 所以 `tools/dump_layout.lua` 导出的并集计划里，这两类控件取的是
  人数最多那一关的几何；`docs/控件坐标表-1600x900.md` 也是这么生成的。
