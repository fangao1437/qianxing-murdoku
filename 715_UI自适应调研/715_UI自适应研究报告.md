# 715 UI 自适应可行性研究报告

截至 2026 年 11 月 17 日。研究对象：千星沙箱 Murdoku 715。

**结论：存在有依据的 UI 自适应实现路径，建议继续实现验证；目前没有理由先判定平台不支持，再退到统一缩小、裁切或玩家手动选比例。官方已提供分设备布局、锚点适配与客户端布局 API，社区也有专门的响应式框架。715 当前尚未将这些能力组成整屏自适应。**[70][71][62]〔L1〕

本轮为资料与代码调研，未修改 715 存档，未进行跨设备实机试玩。以下“可行”指接口与架构依据充分，不表示 715 已适配全部设备。

## 一、摘要与证据等级

- **官方当前资料确认**：PC、移动端、主机端、移动端手柄可分别配置位置、大小、锚点；普通锚点随分辨率保持相对位置，拉伸锚点随容器变化调整尺寸。[71]
- **官方当前 API 确认**：可读取 UI 画布宽高与输入设备，修改客户端控件锚点、位置、尺寸、缩放及父级。没有必要为了 UI 自适应先改成服务器节点图驱动。[70]
- **社区实现存在**：MiliUI 公开检索结果明确提供响应式布局；项目内已有其 ResponsiveLayout 文档缓存，包含百分比、行列、grow、尺寸上下限、宽高比查询和父子锚点实测。详细行为来自旧缓存，本轮未能重新打开仓库全文。[62]〔L4〕
- **715 当前主要阻碍在接线与坐标体系**：固定 1920×1080 设计空间、1600×900 画布假设、静态控件优先、两套棋盘几何，以及部分构建器统一写四端。〔L1〕〔L2〕
- **优先路线**：原生分端配置与功能区锚点，配合轻量 Lua 布局计算；保留现有美术与棋盘比例。首次实现先验证“画布尺寸—父容器—屏幕可见区域”的关系。〔方案判断〕

证据分为：①本轮打开的官方正文；②本轮打开的社区资料；③项目旧缓存中的社区实测；④715及工具源码事实；⑤用户观察；⑥工程方案。相同官方文档的本地缓存与在线正文不算两个独立来源。

用户补充：部分已发布奇域在不同端、不同比例下呈现不同布局。这是支持继续调查的实机观察，但未提供具体奇域、对照设备和截图，不能由此判定其究竟使用分端参数、锚点、Lua 重排还是布局切换。〔用户本轮陈述〕

## 二、平台支持什么

| 能力 | 查证结果 | 对715的意义 |
|---|---|---|
| 分设备布局 | 官方明确四类设备，位置与大小每端单独设置 | 同一玩法可有不同端的布局参数，不必把所有端绑定到同一矩形。[71] |
| 普通锚点 | 分辨率变化时保持相对锚点位置 | 返回键、标题、操作区可稳定贴边或居中。[71] |
| 拉伸锚点 | 随背景或容器大小变化拉伸适配 | 背景、线索视窗、弹窗边界可随可用区域变化。[71] |
| 跟随固有控件 | 官方说明可跟随技能区等，解决19.5:9偏移 | 与原生HUD对齐时可用；不能直接当作客户端内部任意控件锚定功能。[71] |
| 读取画布 | game.GetUICanvasSize() 返回两个number | 可以作为布局输入；官方只写“UI画布宽高”，没有承诺它等于物理分辨率或已扣安全区。[70] |
| 读取设备 | game.GetDevice() 返回当前输入设备类型 | 可决定触屏/手柄交互规格；不是手机型号或宽高比检测器。[70] |
| 客户端布局变换 | SetAnchorMin/Max、SetPivot、SetSizeDelta、SetAnchoredPosition、SetLocalScale | 有能力实现分区移动、尺寸计算与组合缩放。[70] |
| 修改父级 | parent字段标为读写 | 运行时重挂有文档依据；保留坐标、层序、显隐与事件的语义仍须验证，不存在已确认的SetParent方法。[70] |
| 文本适配 | 文本控件有字号自适应、最小字号；有文本视窗 | 应优先保证完整阅读，不能只靠无限缩小字号。〔本地API缓存；L6〕 |

**必须区分三个层次。** 外层“客户端控件容器”本身属于服务器控件；内部客户端控件由 Lua 控制；父子布局又有自己的局部坐标。外层四端参数可以不同，不代表内部已经自动获得合适的排版。〔L6〕[70][71]

官方适配指南要求以移动端16:9作为界面死区检查基准，但这不是所有设备共享的固定安全区尺寸，也不是平板4:3可以不测的理由。官方推荐常用正文20、辅助18、最小16号；这些是平台设计参考，不应直接理解为缩放后的物理像素保证。[71]

## 三、已有自适应实现与资料边界

### 3.1 MiliUI：有现成框架，不是凭空设想

MiliUI 的公开搜索结果将其描述为千星奇域 Lua UI 框架，明确包含 responsive layouts。FAQ搜索摘要说明其可读开发源码不公开，公开仓库提供发布物、文档和示例。因此不将其称作“可随意复制的开源框架”，也不建议本轮直接安装或迁移。[62][66]

项目已有 ResponsiveLayout 缓存完整描述了：Screen根、百分比宽高、Row/Column、grow分配、min/max约束、aspectRatio、按宽高比查询、显式Refresh及嵌套重排。它不是完整CSS布局引擎：不提供自动文本测量、flex-shrink、自动换行布局、自动重挂及常驻轮询。〔L4:3–18、68–220、222–415〕

缓存中的作者运行时实测尤其有价值：

- 父宽由600改为900，横向拉伸子控件从等效540变为840，SizeDelta保持不变。
- 子控件锚点相对直接父控件；父缩放会影响后代视觉尺寸和偏移。
- 2560×1440显示器上300 UI单位约显示472物理像素。该数值只是作者样本，不是通用换算常数。〔L4:20–66〕

这些支持“原生客户端锚点确实能工作”。但该样本不构成715在4:3、16:9、20:9等比例上的成对通过记录。宽高比查询也依赖它读到的画布是否代表实际可用区域，不能仅因有Matches接口就认定检测正确。〔证据边界〕

### 3.2 模拟器、辅助工具能做什么

本轮打开的 miliastra-beyond-simulator 页面说明其有五种PC/手机画布、锚点编辑与触摸模拟，同时明确“模拟器通过不等于真机通过”。可用它预检溢出与几何关系，但不能证明宿主安全区、真实字体、裁剪和输入命中一致。[18]

MiliastraAgent 同样说明体外沙箱不模拟真实引擎渲染、遮罩、字体和全部布局细节。其多端流程可供参考，不是额外一份真机自适应验收。[49]

Lua LSP 提供API补全与类型帮助，但不提供屏幕适配能力本身。[17]

### 3.3 本轮检索范围与未取得的资料

检索覆盖中文“自适应／锚点／屏幕宽高／多端适配”、精确接口名、官方界面布局与客户端API、社区框架与模拟器，以及715脚本和本地构建链。许多搜索结果属于Unity或其他引擎，已排除，不能推导千星沙箱开放了对应接口。

官方动态详情页已用内置浏览器打开，API与布局静态正文亦成功获取。GitHub部分页面先前成功读取，随后MiliUI仓库和FAQ读取超时；更换浏览器读取仓库仍失败，故详细框架行为采用本地旧缓存并标注，没有冒充当前版本核验。[18][49][70][71]〔L4〕

本轮没有取得：具名已发布奇域的跨端实现源码、715跨比例日志、新版MiliUI完整授权条款、宿主安全区统一算法、明确的窗口尺寸变化专用回调。这些空白不等于“不支持”。

## 四、715为什么还没有整屏自适应

| 代码事实 | 适配影响 |
|---|---|
| DESIGN=1920×1080，CANVAS=1600×900，SCALE=5/6 | 只做固定设计坐标换算，不会自然响应可用宽高。〔L1:3567–3606〕 |
| check_canvas只读取一次，不一致只打印告警；读取前即标记checked | 没有把宽高传给布局；首次失败也不会由该函数重试。〔L1:14207–14239〕 |
| apply_rect=false、respect_editor_rect=true | 静态控件通常保留存档几何；只改运行时配置会出现部分移动、部分不动。〔L1:14242–14320、11679–11683〕 |
| apply_rect=true分支直接写入传入矩形 | 会绕过原坐标换算，不能作为“一键适配开关”。〔L1:11670–11673〕 |
| 动态rect默认scale=5/6、canvas_h=900、canvas_w=1600 | 与画布变化没有联动；还需使几何缓存失效。〔L1:11685–11722；子代理核查7167–7190〕 |
| 选关动态内容强制缩放为1、锚点与pivot居中 | 在同一控件上另加缩放或拉伸，会被刷新覆盖。〔L1:11724–11759〕 |
| cell_geometry读取父GetSizeDelta；控制器另按LAYOUT.board计算 | 拉伸时SizeDelta不一定是真宽；两套几何需统一。〔L1:8290–8321、4879–4889〕 |
| GetDevice被缓存，MobileController归touch | 它目前主要影响输入描述，不能直接承担完整分端布局；运行中切输入也需处理缓存。〔L1:11843–11861〕 |
| 原生点击事件转发，格子名附带行列 | 保留原生命中链路较合适；视觉和独立hit层必须同步变换。〔L1:11824–11841、14252–14267〕 |

历史679曾依据一张1280×576手机截图将棋盘平移30，其记录明确说换比例要重测。这证明项目过去采用过固定位置修正，不能当作自适应已完成。历史还记录美术同步函数会覆盖部分父坐标，新布局必须纳入现有写入顺序。〔L5:238–242〕

715审计记录8300条记录、基于714、此次只改4/5/7关相关模块，realGameTest=false。该审计确认设计修改范围，但不证明715所有平台槽位相同，也不证明跨端已验收。〔L3〕

## 五、构建工具是必须同步处理的一环

格式本身可表达分端变换。gil_to_save读取platformType，分别取scale、anchorMin/Max、offset、size、pivot、rotation及syncAllDevices。〔L2a:149–175〕

但apply_plan_to_gil把同一wantX/wantY/w/h写入该控件的全部状态块，并以所有块相同作为验证条件；这会覆盖被修改控件已有的位置和尺寸端间差异。其他旧几何生成器也有同类循环。结论仅针对这些写法，不扩大为“715全档四端完全一样”。〔L2b:90–107、133–138；子代理核查gen.mjs:333–338、add_button.mjs:149–154〕

另外，gil_to_save会重新构造外层sc1，使四端满拉伸且syncAllDevices=true，导出的boxes只按KEYBOARD和固定画布计算。因此直接看这种转换结果，可能漏掉原存档外层的真实适配问题。〔L2a:577–584、606–616〕

后续改造应按明确platformType读写，保留未修改平台与未知字段，按“端间差异应保留”验收；模拟导出需保留原外层几何，或在报告中明确模拟假设。现有tool仓可继续承担编译与存档工作，不要求改用手工节点图；但节点图编译入口不等于客户端响应式布局编译器。〔方案判断；L2〕

## 六、推荐的实现路线

### 6.1 首选：原生分端配置＋功能区布局

保留现有棋盘、美术和玩法逻辑，将首页、选关、线索、棋盘、操作区、弹窗分别定义为有尺寸约束的功能区。优先使用已有容器；若需新容器或重挂，逐一核对查找路径、显隐与层序，不能只包一层就认为完成。〔方案判断〕

- 棋盘保持正方形，格子、家具、墙门、标尺、X标记和命中区使用同一几何来源。
- 线索区宽度设可读下限，长文本使用换行或可滚动区域；调整布局不删除任何线索，也不改变真假与身份规则。
- 操作区按安全边距锚定，触屏下保证触达尺寸；手柄下补测焦点导航。
- 装饰背景可以拉伸或扩大；文字、圆形、票券等不任意做非等比拉伸。
- 宽屏增加功能区之间的空间；高度或宽度不足时由内容最小尺寸触发布局切换，不能只按“手机／电脑”二分。

这是一套组合自适应，不要求四端视觉逐像素相同。实现依据来自原生布局接口与社区父子布局实测。[70][71]〔L4〕

### 6.2 布局计算应围绕可用矩形

以下为拟议算法，未执行或验证：确认可用逻辑矩形为W×H，先扣左右/上下安全边距；主区域给线索、棋盘和操作区分配宽度。三栏成立条件为：

可用宽度 ≥ 线索区最小宽＋棋盘最小边长＋操作区最小宽＋两段间距。

棋盘边长取“扣除侧栏后的剩余宽度”和“扣除标题、工具栏后的剩余高度”的较小值。阈值应由最长线索、7×7格子和触控最小尺寸反推，不直接照抄MiliUI示例的1.55或1.9。

遇到拉伸容器时，几何计算采用父尺寸×锚点跨度＋SizeDelta的关系，并明确该值尚未计父级视觉缩放；也可由布局计算器直接持有解析后的尺寸，避免下游反复猜GetSizeDelta语义。〔L4:37–66；方案判断〕

画布读取先做有效性检查，首次失败允许后续重试。初始显示及页面切换时布局；如证实运行中会改变尺寸，可低频检查尺寸/输入状态，只有变化才重排，不每帧遍历全部控件。没有文档支持的专用resize事件不自行编造。〔方案判断〕

### 6.3 三条路径的选择

| 路径 | 价值 | 决策 |
|---|---|---|
| 原生锚点＋轻量Lua计算 | 最贴近715，保留美术和交互 | 优先验证与接入。 |
| 引入MiliUI发布框架 | 已提供响应式布局抽象 | 作为实现参考或备选；先核验授权、运行时限制、脚本体积与迁移成本。 |
| 整屏等比缩放／手动选择模式 | 改动较小但可能导致文字与触控过小 | 只有主路线遇到明确阻断或可用区域读取失败时才作兜底，不作为当前主方案。 |

不建议复制四整套控件：会增加维护、文本同步与层序成本。分设备参数配置本身是正常适配手段，不等于必须复制四套游戏逻辑。〔方案判断〕

## 七、跨设备验证清单与放行条件

### 7.1 第一阶段：验证宿主映射

先在隔离实验版记录输入类型、GetUICanvasSize、关键父控件尺寸、锚点、位置、缩放；显示边界标记、同父视觉与点击测试控件。此处只是后续验证设计，本轮未生成实验存档。

必须分别验证：同输入端换比例、同分辨率换输入端、同宽高比换分辨率，避免把三个因素混为一谈。至少测一组PC16:9与超宽屏、一组触屏16:9与长屏，另测平板4:3（设备支持时）。

| 观察结果 | 后续动作 |
|---|---|
| 画布宽高确随可用形状变化 | 以画布和实际父矩形驱动响应式布局。 |
| 画布固定，但外层父矩形随比例变化 | 使用可验证的父矩形及锚点关系，不把固定画布比值当屏幕比例。 |
| 两者固定，但可见区域出现裁切/内边距 | 核查外层容器四端参数、死区及宿主缩放；不能直接按W/H分断点。 |
| 输入端切换改变内边距或布局 | 分开处理输入规格与空间规格，重新计算或使用对应平台配置。 |

### 7.2 验证矩阵

| 维度 | 建议覆盖 | 核查重点 |
|---|---|---|
| PC比例 | 16:9、16:10、21:9 | 居中、贴边、上下可见边界 |
| 触屏比例 | 16:9、19.5:9、20:9 | 触控死区、横屏高度、长线索 |
| 平板 | 4:3；其他实际支持比例 | 窄布局重排，不靠强制缩字 |
| 手柄 | PC手柄／主机、移动手柄，按实际支持环境 | 原生内边距、焦点顺序和提示 |
| 分辨率 | 同比例至少两个实际分辨率 | 排除物理像素和UI单位混淆 |
| 页面 | 首页、选关、七关、教程、提示、返回、结算 | 静态与动态布局都覆盖 |
| 生命周期 | 进关、换关、回首页、重开；条件允许时重连/切输入 | 几何缓存、显隐、重复控件、状态恢复 |

### 7.3 放行条件

1. 所有关键文字完整可读，线索不被裁掉或遗漏；7×7最密棋盘仍可识别和点击。
2. 视觉与命中一致，测试边缘格、四角格、按钮边缘、长按、拖动取消、滚动及手柄导航。
3. 棋盘、地板、家具、墙门、X标记同步，选关缩略图刷新后不恢复旧位置。
4. 旧构建工具重新生成后仍保留端间差异；读取四端实际字段，不能只看第一个状态块。
5. 同尺寸重复刷新不创建额外控件、不累积缩放；记录控件数量与布局触发次数。
6. 715关卡文字、线索集合、身份规则与解题状态不因UI改造改变。
7. 离线几何/模拟器结果与真机结果分别标注。没有测试的设备明确列为未测，不写“兼容所有玩家”。

## 八、结论与建议

**本轮已回答首要问题：有UI自适应能力，也有面向千星奇域的现成响应式实现参考。** 官方分设备布局、锚点和客户端API可相互印证；用户观察进一步支持继续沿这条路线推进。[70][71][62]

**对715的建议是进入最小实机验证，然后接入功能区布局。** 当前最大未知是可用区域映射，不是“能否移动或缩放UI”。最大工程风险是静态/动态布局所有权混杂、四端参数被旧工具覆盖、视觉与命中层脱离。〔L1〕〔L2〕

本轮没有改715、没有输出716、没有安装框架、没有操作游戏、没有推送或发布。新增的是本研究报告及其Word/PDF版本。原有设计文档保持原样，本报告不宣称它们已同步成自适应设计。
