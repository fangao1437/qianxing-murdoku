## 一 结论先说

**这是"门墙那个坑"的下一层，而且当年那套修法现在其实已经失效了。**

1. 机制同一个：`visible=false` 作用在 `cell.*` 上 ⇒ `hide_kids()` **递归**藏掉该格全部子控件，且**只藏不显**；
2. 当年给 `wall.*/door.*` 写了"把该亮的边记下来、每帧重放"的修法（`_edge_want`），
   但它挂的 `_cells_paint` **现在只在建控件时被调用**（注释里"每帧调用"是旧行号时代的，早就不准了）
   ⇒ 那套重放**等于没有**；
3. `obj`（家具/障碍物）连重放都没写 ⇒ 被藏过就整关不画；
4. **为什么只有第一次进第一关坏**：第一关的 `cell.*` 是这一帧新建的 ⇒ 会走一次 `false → true`
   ⇒ 触发递归藏；第二关起**不重建格子** ⇒ 不触发 ⇒ "换关回来就好了"（与用户描述逐字对上）。

修法 = **两半都要有**：

- **第一半（v280）**：把家具的意图记进 `_obj_want`，画法收成 `Adapter:_paint_obj`（只有一份）；
- **第二半（v281，真正生效的那一半）**：`cell.*` 由藏转显时置 `_overlay_dirty`，
  由 **`Adapter:on_tick`**（`main.lua` 的 `on_update` 每帧调它）调 `_repaint_cell_overlays`
  重放「门墙 + 家具」两份意图。**事件驱动 ⇒ 稳态零成本**。

## 二 机制（逐环都有仓内出处）

| 环 | 事实 | 出处 |
|---|---|---|
| ① | `set_property(…,"visible",false)` 且 id 以 `cell.` 开头 ⇒ `hide_kids(ctrl,0)` 递归把所有子控件设 `visible=false` | `engine_adapter_qianxing.lua` 的 `visible` 分支 |
| ② | 显示方向**不递归**（既有设计："子控件各有负责人"）⇒ 被藏过的子控件**必须有人重新点亮** | 同上（那段注释） |
| ③ | `face` 有人点；`wall.*/door.*` 曾有"每帧重放"；**`obj` 从来没人点** | `_edge_want` / `_cells_paint` 的长注释 |
| ④ | **但 `_cells_paint` 现在只在 `create_control` 与 `ensure_cells` 里被调用** ⇒ 那套"每帧重放"失效 | 全仓 `grep _cells_paint`（2 个调用点，都在建控件路径上） |
| ⑤ | 第一关"本次新建 25 个"；之后任何一关"本次新建 0 个" | 仓内真机日志引文（`ui_controller.lua` 里 `retry_more` 的注释） |

⇒ 症状链：**新建格子 →（主页）`visible=false` → 递归藏 → 回关卡 `visible=true` →**
**`face` 有人点亮、`obj`/墙门没人 → 家具/障碍物整关不画 → 换关（不重建格子）就好** ✓

## 三 改了什么（只动适配层）

| 位置 | 改动 |
|---|---|
| `set_property` 的 `object` 分支 | 顺序倒过来：**先**解析"这一格该显示什么"（调色板 `obj.<kind>`）并记进 `self._obj_want[id]`（`false` = 没有物件），**再**尽力画一次。子控件此刻取不到也不丢意图 |
| 新增 `Adapter:_paint_obj(cell_id, ctrl, want, force)` | 家具**唯一**的画法（分支与重放共用）：换图/换色按 `_obj_marks`（弱键）只在意图变化时写；`SetVisible(true)` **每次重放都写**（`hide_kids` 会绕过脚本改它，缓存会骗自己）；`SetActive(true)` 只在换图那一次写 |
| 新增 `Adapter:_repaint_cell_overlays(cell_id)` | **重放的唯一入口**：① 门墙（`_edge_want` → `SetVisible`）② 家具（`_obj_want` → `_paint_obj`）。`_cells_paint` 与 `on_tick` 都调它 |
| `set_property` 的 `visible` 分支 | `vis == true` 且 `cell.*` ⇒ `self._overlay_dirty = true`（**只在显示方向**：隐藏方向没有要救的东西） |
| `Adapter:on_tick` | `_overlay_dirty` ⇒ 清标记 + 对 `_edge_want` / `_obj_want` 里记过的格子各重放一次（去重）。**稳态零成本**（与既有 `_subtree_dirty` 同一个套路） |

纪律（都写进注释）：**画法只有一份**、**重放只有一份**、**每帧入口必须是 `on_tick`**、**`object=false` 不许被点亮**（白板压头像的老 bug）。

## 五 为什么"门墙修过而家具没修"，以及为什么这次第一版也没修好

- **当年**那段修法的判据写得窄：`ui_controller.lua` 的补发注释原文
  「依据：`Adapter:_apply_edges` 的 `missing_sub` 只出现在 `wall.*` / `door.*`」——
  它说的是"**属性补发额度**只给墙门"，却被读成"**只有墙门会被递归藏影响**"。两件事不是一回事。
- **这次第一版**（v280）把重放挂回 `_cells_paint`，是**照着旧注释**"每帧都会跑的那条路"抄的；
  而代码里它已经只在建控件时跑了 ⇒ **注释与代码漂移**导致修法空转（离线用例当时也是绿的，
  因为用例自己手动调了 `_cells_paint` —— **这正说明"用例替被测代码走了那一步"时绿灯不算数**）。

⇒ **三条教训**（已写进 `技术架构.md` §7.6）：

1. 修"某图层不显示"时，要按"**谁重放这一层的意图**"逐个清点图层，而不是只修被报的那一个；
2. **"每帧调用"必须去数调用点，不能信注释**（本项目的老毛病，这次又中一次）；
3. **用例不许替被测代码补关键一步** —— 否则"挂在永远不会被调用的函数上"也能全绿。

## 六 同类隐患（未观察、未改，留判定依据）

`note` / `x` / `hint` 三个子控件也只在"值变化"时下发，机制相同**但触发窗口不同**：
开局它们是空的（没有笔记/✗/提示），等玩家操作时才下发 ⇒ 那时已经过了 `false→true` 那道坎。
**唯一例外**：若开局就带着**存档里的 ✗ / 笔记**（例如从服务端 `RESTORE` 回来），第一关可能同样被藏。
目前**没有观察到**，也**没有真机证据**。

由 `_repaint_cell_overlays` 一起重放（只需重放 `SetVisible`，文字不必重写）。
